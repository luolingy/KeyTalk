### 方案 B 已完成：命令行可运行闭环

在 Gio 界面（S7）之前，先做了一个**可运行的命令行版本**来验证整条链路。
这不替代 S7，但提供了：

- 一个**现在就能跑**的东西（`cmd/keytalk`），不必等到 UI 完成；
- 一条**最短的排错路径**：出错时能明确区分"加密/网络错了"还是"UI 错了"；
- 跨模块的回归测试（`internal/e2e`），守护四层协作的行为。

**已验证的行为**（`internal/e2e` + `e2e.ps1`）：

| 验证项 | 结果 |
|---|---|
| 两个独立进程通过 mDNS 互相发现 | ✅ |
| 自动完成 M2 握手（双方均校验身份） | ✅ |
| 双向加密文本消息，字节一致 | ✅ |
| 30 条消息严格保序、无丢失 | ✅ |
| 陌生身份接入被拒绝 | ✅ |
| 攻击尝试后合法流量不受影响 | ✅ |

**实测中发现的真实缺陷**（均已修复并加测试守护）：

1. **入站连接按 IP 匹配导致会话劫持**
   传输层原按来源 IP 识别入站对端。同一台机器（或同一 NAT 后）的
   任意进程共享 IP，于是一个恶意连接会被误认为真实对端、
   **顶替**其连接，随后关闭时连带摧毁真实会话。
   攻击者无需任何密码学能力即可造成拒绝服务。
   修复：入站连接一律视为未知来源，只有握手验签后才确立身份
   （`Transport.AdoptConnection`）。

2. **mDNS 在多网卡机器上只对最后一个接口生效**
   `SetMulticastInterface` 是**有状态**的，循环调用后只有最后一次生效。
   在多网卡机器（WLAN + VMware + WSL + VPN）上，宣告被发到虚拟网卡，
   真实局域网上的对端收不到——表现为"发现静默失败"。
   修复：每个接口各建一个 socket。

3. **按来源 IP 过滤自身，导致同机双实例无法互见**
   过滤逻辑应基于**指纹**（报文内容）而非 IP（信封）。
   同机多用户或本机联调是完全合法的场景。

4. **端口 5353 冲突导致发现不可用**
   mDNS 规范要求绑定 5353，而同机常有其他 mDNS 服务。
   修复：`SO_REUSEADDR`（Windows）/ `SO_REUSEADDR + SO_REUSEPORT`（Unix）。
   RFC 6762 §15.1 明确讨论了多进程共享 5353。

5. **多候选地址未累积**
   同一次宣告会从多个接口各到达一次，来源 IP 不同。
   只保留最后一个会选中不可路由的虚拟网卡地址。
   修复：累积全部候选地址，逐个尝试连接。

6. **握手在公钥不匹配时无限挂起**
   对端无法解密时会**静默丢弃**（协议上没有"我解不开"这种回应，
   因为它会向攻击者泄露信息）。发起方因此永远等不到响应。
   修复：20 秒超时 + 明确错误提示（`ErrHandshakeTimeout`），
   把静默失败转成用户可见的事实。

7. **同时发起握手（glare）把已建立的会话报告为失败**
   双方几乎同时通过 mDNS 发现对方，于是都发出 KEM_INIT。
   原实现直接接受对方的 INIT 并覆盖本地 pending，
   导致自己的超时定时器稍后触发，把**刚刚建立成功**的会话报告为失败。
   修复：确定性的平局规则（指纹大的一方让步），并取消让步方的定时器。

8. **事件通道被两个消费者竞争，帧被"旁观者"吃掉**（最难查的一个）
   `session.Manager` 独占消费 `transport.Events()`，而 CLI 又起了一个
   goroutine 读同一通道，两者随机抢事件，约一半的帧进了 CLI 那里。
   症状是传输层明明 `read 771 bytes`，会话层却毫无反应——
   看起来像传输层丢包，实际是上层把帧抢走了。
   修复：只保留一个消费者；CLI 改为轮询只读快照 `Peers()`。

9. **多网卡环境下双方各自拨号，连接对不上**
   双方都主动连接会产生两条 TCP 连接，在多网卡机器上可能走不同网卡，
   于是应答发到另一条路径上。表现为**随机**超时（实测 10 次失败 6~7 次）。
   修复：分角色——指纹较大的一方主动连接，较小的一方被动等待。

10. **IPv6 zone 标识破坏 peerID**
    Windows 的 `RemoteAddr()` 形如
    `169.254.201.140%VMware Network Adapter VMnet8:62733`，
    含空格与中文，被当作路由键后导致帧无法归属。
    修复：构造 peerID 前剥离 zone。

> **这些缺陷没有一个能被单元测试发现。** 全部来自"两个真实进程
> 在真实多网卡机器上反复运行"。`e2e.ps1` 因此不是可选项——
> 它跑 8~12 次全绿，才有资格说"这条链路是稳的"。
> 本机实测在这轮修复前后：**0/10 → 12/12**。

- M2 ratchet 的**主动轮换**（`REKEY` / `REKEY_ACK` 的发起与接收路径）——当前 `Epoch` 机制与 `prev` 代次接收已就绪，但轮换触发逻辑未写。

**生产替换提醒**：仓库内 `pgp_provider.go` 基于已废弃的 `golang.org/x/crypto/openpgp`，**仅 RSA**，只适合测试。生产构建须替换为 `github.com/ProtonMail/go-crypto/openpgp`（支持 Ed25519 + cv25519）。替换只需实现 `IdentityProvider` 接口，不影响其他模块。详见 [crypto-protocol.md](crypto-protocol.md) §10.4.1。

## S2 · `crypto` 包（TDD，无网络无 GUI）

这是**最应该先做扎实**的部分，因为它决定安全性且完全可离线验证。

### 任务

1. `identity.go`：生成 / 导入 / 导出身份密钥；指纹计算与格式化。
2. `pgp.go`：KEM 封装 / 解封（**M2 方案**，见 [crypto-protocol.md](crypto-protocol.md) §5）。
3. `aead.go`：HKDF 派生 + ChaCha20-Poly1305 封装 + nonce/AAD 构造。
4. `session.go`：会话结构、双向密钥、seq、重放窗口、握手、ratchet。
5. `keystore.go`：口令派生（argon2id）、私钥落盘加密、解锁。

### 验收

必须通过 [crypto-protocol.md](crypto-protocol.md) §13.1 的**全部**用例，特别是：

- [ ] M2：**泄漏 IK 私钥后无法重建旧 SK**（PFS 验证）
- [ ] 重放报文被拒且计数
- [ ] 乱序窗口内全部接受、窗口外拒绝
- [ ] 篡改密文/AAD/tag 全部失败
- [ ] `recipient_fp` 不匹配被拒
- [ ] 陈旧 `ts` 被拒
- [ ] `sid` 复用被拒
- [ ] ratchet 后旧密钥无法解新消息
- [ ] `Session.Close()` 后密钥全零
- [ ] 生成的公钥可被 `gpg --import` 导入

### 注意

- 此阶段**不要**接触网络代码，保持纯净可测。
- **不要**为了"以后可能有用"提前实现群聊/多设备相关逻辑。

1. `files/chunk.go`：分块 AEAD（STREAM 构造，`index` 进 nonce/AAD，末块 `is_final`）。
2. `files/send.go` / `recv.go`：发送/接收编排、位图、磁盘检查、流式哈希。
3. `wire/file.go`：新增 `FILE_*` Kind。
4. **两级优先队列**（[attachments.md](attachments.md) §6.2）：文本/控制帧高优先级，附件块低优先级。
5. 令牌桶限速（给聊天留带宽）。
6. UI：附件卡片、进度、打开/另存为、拖放。
7. **续传**（可选，字段已预留）：位图持久化 + `FILE_ACCEPT` 带位图。

### 验收

必须通过 [attachments.md](attachments.md) §15 的全部用例，特别是：

- [ ] **重排两块 → 解密失败或哈希不匹配**
- [ ] **丢弃尾部块 → 因缺 `is_final` 块而拒绝**
- [ ] **重复投递同一块 → 被拒绝并计数**
- [ ] `file_hash` 不匹配 → 拒绝
- [ ] 传 1 GB 文件时**内存恒定**，不随文件增长
- [ ] 传大文件时发聊天消息，延迟 ≤ 约一个 64 KiB 块的传输时间
- [ ] 磁盘空间不足 → `FILE_REJECT`，不开始传
- [ ] 存盘路径不含对端提供的文件名
- [ ] 令牌桶限速实测生效

### 里程碑

**M4：附件传输可用**（限定大小上限内）。

> **前置决策**：中继是否允许传大附件（[nat-traversal.md](nat-traversal.md) §9.2）。若 S11 已完成，此决策必须先定。

## S11 · 公网穿透与中继（二期）

### 任务

按 [nat-traversal.md](nat-traversal.md) 实现：

1. `transport/ice`：基于 pion 的 ICE + DTLS + DataChannel 传输。
2. NAT 行为探测（多 STUN 对比 + **至少 3 个服务器多数投票**，[nat-traversal.md](nat-traversal.md) §2.5），结果缓存。
3. **STUN 配置为有序列表**：自建优先、公共兜底（[nat-traversal.md](nat-traversal.md) §4.2）。
4. **延迟收集 relay 候选**（§6.1）：先试直连，失败再启用中继。
5. `sig/`：WebSocket 信令客户端 + **信令消息签名/验证**（§8.2）。
6. 部署 STUN/TURN（`pion/turn` 或 coturn）+ 会合服务。
7. 连接路径上报（直连/中继）与 UI 展示。
8. 中继成本控制：带宽限制、时长限制、并发限制、认证。
9. ICE restart（网络切换，§11.2）。
10. **中继→直连升级**（§7，建议实现）。

### 验收

- [ ] 见 [nat-traversal.md](nat-traversal.md) §13.1 的 **NAT 组合矩阵**（含对称 NAT × 对称 NAT → 中继）
- [ ] IPv6 双方可用时走直连，不占用中继
- [ ] **篡改信令消息 → 签名验证失败，拒绝该候选**
- [ ] 伪造候选地址注入 → 验证失败；即使通过，应用层指纹校验兜底
- [ ] TURN 不可达 → 明确报错，不静默失败
- [ ] **所有 STUN 不可达 → UI 显式提示，不静默退化**
- [ ] **自建 STUN 不可达时可自动切到公共 STUN**（反之亦然）
- [ ] **≥3 个 STUN 多数投票**，单台异常不影响 NAT 行为判定
- [ ] 直连成功时**未在中继上产生分配**（验证延迟收集生效）
- [ ] 网络切换（WiFi→蜂窝）→ ICE restart 成功
- [ ] 中继带宽/时长限制生效
- [ ] 长期中继会话触发限制并重试直连

### 里程碑

**M5：跨网络可用**（公网互通，含中继兜底）。

### 注意

- **这是唯一需要运维基础设施的阶段**。上线前需明确：服务器成本归属、日志留存策略、滥用处置流程。
- 自建 TURN 的元数据仍暴露给运营者（[threat-model.md](threat-model.md) §4.7），需在隐私说明中告知。
- STUN 建议与信令共用同一台 VPS（成本可忽略），并把公共 STUN 作为兜底（[nat-traversal.md](nat-traversal.md) §4.2）。
- **若面向中国大陆用户，公共 STUN 可达性不具备保障，自建 STUN 是必需项而非优化项。**

| duress 模式 | 超出范围 |
| 抗内存取证 | Go 语言限制，见 [crypto-protocol.md](crypto-protocol.md) §10.5 |

## 附录 C · 建议的下一步

1. **执行 S0**，尤其是 S0.2（Android mDNS）。这是首期唯一可能推翻架构的风险点。
2. 若 S0 全部通过 → 进入 S2（crypto 包），以 TDD 方式推进。

4. **S11（公网）启动前**，需先完成四项决策：
   - **STUN 用公共还是自建**（建议自建为主 + 公共兜底，[nat-traversal.md](nat-traversal.md) §4.2）；
   - 中继是否允许传大附件（[nat-traversal.md](nat-traversal.md) §9.2）；
   - 服务器成本归属与预算；
   - 服务器日志留存策略（决定元数据暴露程度，[threat-model.md](threat-model.md) §4.7）。
