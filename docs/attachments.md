# 附件传输设计

> 本文回答："怎么发文件？"
> 首期不实现，但相关字段与帧类型已预留（见 §7）。

---

## 1. 需求与约束

**需求**：发送任意大小的文件，加密、可取消、可显示进度、尽量支持断点续传。

**约束（来自现有设计）**：

| 约束 | 来源 | 影响 |
|---|---|---|
| `MAX_FRAME = 1 MiB` | [wire-protocol.md](wire-protocol.md) §1 | 文件必须分块 |
| 单帧长度前缀 + AEAD tag | 同上 | 无法"整体加密后切块" |
| 发送队列有界（256 帧）且满时背压 | [transport-lan.md](transport-lan.md) §4.3 | 大文件会撑满队列，必须限流 |
| 纯 P2P，无离线存储 | [transport-lan.md](transport-lan.md) §7 | 对方必须在线才能收 |
| 消息正文以密文入库 | [architecture.md](architecture.md) §5.1 | 附件同理 |

**核心难点**：**分块加密必须能防重排、防截断、防重放**，而 AEAD 的 tag 只保护单块。

## 2. 为什么不能用两个"显然"的做法

### 2.1 做法一：整个文件加密后切成帧

```
ct = AEAD(key, nonce, 整个文件, aad)
然后按 1 MiB 切块传输
```

**不行**：接收方无法边收边解密——必须拿到**完整的** `ct` 才能验证 tag 并解密。这意味着 1 GB 的文件要在内存里放 1 GB（加密前+加密后共 2 GB），而且最后一块到达前什么都做不了。

### 2.2 做法二：每块独立随机 nonce，彼此无关联

```
for each chunk:
    nonce = random(12)
    ct_i = AEAD(key, nonce, chunk_i, nil)
```

**不行**，因为存在三类攻击：

| 攻击 | 后果 |
|---|---|
| **重排** | 攻击者交换块 i 与块 j 的顺序，接收方解出乱序内容 |
| **截断** | 攻击者丢弃尾部若干块，接收方以为文件只有这么长 |
| **重放** | 攻击者重复投递某块（对某些格式可能造成危害） |

每块的 tag 只能证明"这一块没被改动"，**不能证明"块与块的关系没被改动"**。

## 3. 分块 AEAD 设计（STREAM 构造）

采用与 [age](https://age-encryption.org/) 的 STREAM 构造相同的思路：**让每一块都声明自己在整个文件中的位置与总量**。

### 3.1 参数

| 参数 | 值 | 理由 |
|---|---|---|
| `file_key` | 32 字节随机 | 每文件独立（§4） |
| `file_id` | 16 字节随机 | 文件标识，也用于 AAD 绑定 |
| `chunk_size` | **64 KiB** | 见 §3.4 |
| `file_hash` | SHA-256（32B） | 整体完整性（§5） |

### 3.2 每块的封装

```
nonce_i = index(11B, big-endian) ‖ is_final(1B)
          ↑ 11 字节计数        ↑ 0x00 = 非末块, 0x01 = 末块

aad_i   = ver(1B) ‖ file_id(16B) ‖ index(8B) ‖ total_chunks(8B) ‖ file_size(8B)

ct_i    = ChaCha20Poly1305.Seal(file_key, nonce_i, chunk_i, aad_i)
```

### 3.3 三类攻击如何被阻断

| 攻击 | 防护机制 |
|---|---|
| **重排** | `index` 同时进入 nonce 与 AAD。交换块 i/j 后，第 i 位上的密文是用 `index=j` 的 nonce 加密的，接收方用 `index=i` 重建 nonce → **解密失败** |
| **截断** | ① `total_chunks` 在 AAD 中，接收方知道自己应收到多少块；② **仅最后一块**的 `is_final = 1`，若攻击者丢弃尾部，接收方**收不到带 final 标志的块**；③ `file_hash` 在收齐后校验 |
| **重放** | 接收方按 `index` 写入，同一 `index` 重复到达时**拒绝并计数**（配合 [crypto-protocol.md](crypto-protocol.md) §8 的会话级重放窗口——附件块本身也是 SECURE 帧，已被会话窗口保护一层） |

> **注意**：`index` 用 8 字节（而非 4 字节）在 AAD 中，是为了与 `total_chunks` 类型一致并留出充足空间。`nonce` 中的 index 只需 11 字节，对 64 KiB 块而言远超实际需求（2^88 块）。

### 3.4 为什么 chunk_size = 64 KiB

| 候选 | 优点 | 缺点 |
|---|---|---|
| 16 KiB | 调度延迟低 | 每块固定开销占比升高 |
| **64 KiB** | 开销可忽略；延迟可接受 | — |
| 256 KiB | 吞吐略优 | 慢链路下调度延迟大（见 §6.2） |
| 1 MiB | 吞吐好 | 等于 `MAX_FRAME`，无余量；延迟大 |

**每块固定开销**：帧头约 29B + tag 16B ≈ 45B。对 64 KiB 块是 **约 0.07%**，可忽略。

**为什么关心延迟**：见 §6.2——附件块与聊天消息共享发送通道，块越小，聊天消息被插入的机会越多、等待越短。

### 3.5 【重要】不要自己发明构造

STREAM 类构造看似简单，但"末块标志如何编码""计数器如何防回绕"这类细节极易出错。建议：

- **参考 `filippo.io/age` 的 STREAM 实现**（BSD-3-Clause）对照设计；
- 注意：age 的 stream 包是 `internal`，**不能直接 import**，只能参考其设计自行实现；
- 若不想自行实现，可评估直接使用 age 库完成"文件级"加密，但那样会失去与消息流的集成能力。

> **不确定项**：age 的 STREAM 具体字节布局（计数器宽度、末块标志的确切位置）我无法离线核实，标注为"设计参考"而非"照抄规范"。实现时请以 age 源码为准。

## 4. 为什么 `file_key` 必须独立于会话密钥

一个自然的想法是"从会话密钥 HKDF 派生 `file_key`"。**不要这样做**，理由：

| 问题 | 说明 |
|---|---|
| **转发** | B 想把收到的附件转发给 C。若 `file_key` 是从 A↔B 的会话派生的，B 无法在 A↔B 会话结束后复用；而独立的 `file_key` 可以随转发消息重新加密发给 C |
| **断点续传** | 重连会重新握手，会话密钥变了（[transport-lan.md](transport-lan.md) §5.2）。若 `file_key` 依附会话密钥，续传时所有已收块都要作废 |
| **多接收方** | 二期若要"发给多人"，独立 `file_key` 可多次分发 |
| **ratchet 干扰** | 会话 ratchet 会更换密钥，长传输可能跨越多次 ratchet |

**结论**：`file_key` = 每文件一次 `crypto/rand`，随 `FILE_OFFER` 经会话 AEAD 加密传输，并在发起方本地持久化直到传输完成。

## 5. 整体完整性：`file_hash`

分块 AEAD 已保证每块真实且位置正确。`file_hash` 补充保证：

- **总量正确**（收齐后比对）；
- **发送方声明的哈希与实际内容一致**（防止发送方事后抵赖或元数据不一致）。

```
发送方：file_hash = SHA-256(整个文件明文)      ← 流式计算，不占额外内存
接收方：边收边更新 hasher，收齐后与 FILE_OFFER 中的值比对
```

**注意**：`file_hash` 在 `FILE_OFFER` 中就声明（而非结束时），这样接收方可以边收边算，且**在传输前就能判断内容是否与预期一致**（若发送方同时通过其他渠道告知了哈希）。

**收齐的定义**：收到 `index` 从 `0` 到 `total_chunks-1` 的**全部**块，且最后一块带 `is_final` 标志，且 `file_hash` 匹配。缺一不可。

## 6. 传输路径：共享通道 + 优先级调度

### 6.1 决策：首期不引入独立通道

一个附件可能涉及数千个块。若与聊天消息共用 FIFO 队列，会造成**队头阻塞**：用户在传 1 GB 文件时，聊天消息要等所有块发完。

两种解法：

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 独立传输通道** | 另开 TCP 连接 / DataChannel | 隔离彻底，但需 `Transport` 支持多路复用，且新连接需要**重新认证**（额外握手协议）。复杂度高 |
| **B. 单通道 + 应用层优先级调度** | 发送队列分两级，附件块为低优先级 | 实现简单，效果足够。**推荐首期采用** |

**方案 A 的隐藏成本**：新连接必须证明"我是刚才那个已认证的对端"。这需要一个基于现有会话密钥的**会话恢复协议**（HMAC 挑战-应答），是独立的设计工作。首期不值得。

**方案 A 的备选形态**：WebRTC 的 DataChannel 天然是 SCTP 多流，开第二个 DataChannel 即可获得传输层隔离，不需要额外认证（同一 DTLS 关联）。**若公网阶段采用 pion，方案 A 的成本会显著降低**，届时可重新评估。

### 6.2 优先级调度设计

```
发送队列：
┌─────────────────────┐
│ 高优先级队列（FIFO）  │  ← 聊天消息、控制帧、FILE_OFFER/ACCEPT/END
├─────────────────────┤
│ 低优先级队列（FIFO）  │  ← FILE_CHUNK
└─────────────────────┘

调度规则：
  1. 高优先级队列非空 → 取一个发送
  2. 否则低优先级队列非空 → 取一个发送
  3. 都空 → 等待
```

**效果**：一条聊天消息最多等**一个**附件块发完。

**延迟计算**（这正是 §3.4 选 64 KiB 的原因）：

| 链路速率 | 一个 64 KiB 块的传输时间 |
|---|---|
| 10 Mbps | ~52 ms |
| 2 Mbps | ~260 ms |
| 1 Mbps | ~520 ms |
| 500 Kbps | ~1.05 s |

即使 500 Kbps 的慢链路，聊天消息最坏延迟约 1 秒——可接受。若用 256 KiB 块，则变成 4.2 秒，明显变差。

### 6.3 附件限速

即使有优先级调度，**带宽仍是被占满的**——聊天消息虽然插队，但整体吞吐被附件挤压，会导致 ping 升高、体验下降。

**建议**：附件传输主动限速，**留出余量给聊天**：

- 首期：固定限速（可配置），如"限制附件占用不超过 ~70% 的估计带宽"；
- 二期：自适应（根据 ACK 往返延迟动态调整）。

**如何实现限速**：在低优先级队列的调度处加**令牌桶**，而不是在应用层 sleep。令牌桶可以平滑发送，避免突发。

### 6.4 背压

附件发送端必须响应背压：

- 传输层队列满（[transport-lan.md](transport-lan.md) §4.3）→ 暂停发块，等待；
- **不要**用阻塞等待，而是让发送循环在队列满时回到调度器，重新评估优先级。

## 7. 协议消息

新增 `Kind`（均为 `SECURE` 帧，见 [wire-protocol.md](wire-protocol.md) §4）：

| Kind | 名称 | 字段 |
|---|---|---|
| `0x10` | `FILE_OFFER` | `file_id(16B)‖name_len(2B)‖name(UTF-8)‖size(8B)‖mime_len(2B)‖mime‖chunk_size(4B)‖total_chunks(8B)‖file_hash(32B)‖file_key(32B)` |
| `0x11` | `FILE_ACCEPT` | `file_id(16B)‖bitmap_len(4B)‖bitmap` （空位图 = 从头开始） |
| `0x12` | `FILE_REJECT` | `file_id(16B)‖reason(1B)` |
| `0x13` | `FILE_CHUNK` | `file_id(16B)‖index(8B)‖ct(变长)` |
| `0x14` | `FILE_END` | `file_id(16B)` |
| `0x15` | `FILE_DONE` | `file_id(16B)` |
| `0x16` | `FILE_CANCEL` | `file_id(16B)‖reason(1B)` |
| `0x17` | `FILE_ERROR` | `file_id(16B)‖code(1B)` |

**注意**：以上字段**全部位于 SECURE 帧的加密载荷内**，因此文件名、MIME、`file_key` **自动受会话 AEAD 保护**，无需额外加密。这是把附件协议放在应用层加密之内带来的直接好处。

`reason` 取值：`0x01` 用户拒绝 / `0x02` 磁盘空间不足 / `0x03` 超过大小限制 / `0x04` 不受支持的 MIME（可选黑名单）/ `0x05` 仅中继可达且文件过大（见 [nat-traversal.md](nat-traversal.md) §9.2）。

## 8. 完整流程

```
A                                          B
│                                          │
│ 1. 读文件元数据，生成 file_id / file_key   │
│ 2. 流式计算 file_hash（不读入内存）         │
│ 3. 计算 total_chunks                       │
│                                          │
│ ──── FILE_OFFER ────────────────────────▶│
│                                          │ 4. 检查磁盘空间
│                                          │    检查大小限制
│                                          │    检查信任状态（BLOCKED 则拒）
│                                          │    等待用户确认（可配置自动接受）
│ ◀─── FILE_ACCEPT { 空位图 } ─────────────│
│                                          │
│ 5. 循环：读块 → 加密 → 入低优先级队列       │
│ ──── FILE_CHUNK × N ────────────────────▶│ 6. 解密 → 校验 index → 写盘
│      （受令牌桶限速、受背压暂停）            │    更新位图
│                                          │
│ ──── FILE_END ──────────────────────────▶│ 7. 校验：块齐 + final 标志 + file_hash
│                                          │
│ ◀─── FILE_DONE ──────────────────────────│
│                                          │
   （任一方可随时 FILE_CANCEL）
```

### 8.1 用户确认

接收方在 `FILE_OFFER` 后应**询问用户**（除非已配置为自动接受来自 VERIFIED 联系人的小文件）。

**必须展示的信息**：文件名、大小、发送者身份与**信任状态**。

**理由**：未验证联系人发来的文件，用户需要知道自己面对的风险（[threat-model.md](threat-model.md) §4.1）。

### 8.2 自动接受的边界

建议允许"自动接受"仅当：

- 联系人状态为 `VERIFIED`，**且**
- 文件小于阈值（如 5 MB）。

`TOFU` 状态**不应**自动接受——否则未验证联系人可无声写入大量数据。

## 9. 断点续传

### 9.1 机制

- 接收方持久化**已完成的块位图**；
- 连接中断后重新握手（新会话），发起方重新发送 `FILE_OFFER`（**同一 `file_id`、同一 `file_key`**）；
- 接收方回 `FILE_ACCEPT` 携带位图；
- 发起方从缺失块继续。

### 9.2 位图大小

`total_chunks / 8` 字节：

| 文件大小 | 块数（64 KiB） | 位图大小 |
|---|---|---|
| 10 MB | 160 | 20 B |
| 100 MB | 1600 | 200 B |
| 1 GB | 16384 | 2 KB |
| 10 GB | 163840 | 20 KB |

最大 20 KB，完全可以直接放进 `FILE_ACCEPT`（仍在 1 MiB 帧限制内）。**不需要更复杂的编码**。

### 9.3 关键约束

- **`file_key` 必须复用**。若发起方重新生成 `file_key`，已传块全部作废。
- 发起方需**持久化 `file_key` 与 `file_hash`** 直到传输完成（进程重启也不能丢），否则续传不可能。
- 若发起方已丢失这些信息（如重装了应用），只能从头发起，并显式告知用户。

### 9.4 是否首期实现

**建议不实现**。可靠性价值明确，但涉及额外的持久化与状态管理。首期先做"中断即失败，用户可重发"。设计上保留 `FILE_ACCEPT` 的位图字段（空位图 = 从头），使二期可无痛加入。

## 10. 存储设计

### 10.1 目录布局

```
<config>/attachments/<file_id_hex>/
    data      ← 已加密的块（连续写入，或按 index 分片）
    state     ← 位图 + 已收字节数 + file_hash 中间状态（续传用）
```

**关键**：**从不使用对端提供的文件名作为路径**。文件名只用于**显示**。这从根本上杜绝路径穿越（`../../etc/passwd`）与非法字符问题。

### 10.2 存密文还是明文

| 方案 | 优点 | 缺点 |
|---|---|---|
| **存传输时的密文** | 零额外开销；与消息正文策略一致 | 每次读取都要解密；依赖 `file_key` 可用 |
| 存明文（另用本地密钥加密） | 读取简单 | 需要二次加解密整个文件 |

**推荐：存密文**（零开销），并把 `file_key` 用主密钥加密后存入 DB（§11）。

### 10.3 数据库表

```sql
CREATE TABLE attachments (
    file_id      BLOB PRIMARY KEY,      -- 16B
    message_id   INTEGER REFERENCES messages(id),
    peer_fp      TEXT NOT NULL REFERENCES contacts(fingerprint),
    direction    INTEGER NOT NULL,      -- 0=in 1=out
    name_ct      BLOB NOT NULL,         -- 文件名，用 MK 加密
    name_nonce   BLOB NOT NULL,
    mime_ct      BLOB,
    size         INTEGER NOT NULL,
    chunk_size   INTEGER NOT NULL,
    total_chunks INTEGER NOT NULL,
    file_hash    BLOB NOT NULL,
    file_key_ct  BLOB NOT NULL,         -- file_key，用 MK 加密
    file_key_nonce BLOB NOT NULL,
    state        INTEGER NOT NULL,      -- 0=offering 1=transferring 2=complete 3=failed 4=cancelled
    received     INTEGER NOT NULL DEFAULT 0
);
```

**注意**：`name_ct` 与 `file_key_ct` 用**主密钥 MK** 加密（见 §11），而非会话密钥——因为会话结束后本地仍需读取这些数据。

## 11. 【重要】引入主密钥（MK）层

### 11.1 问题：改口令会让数据不可读

一个自然的做法是用**口令经 argon2id 派生的密钥（KEK）**直接加密数据。若照此推广到附件：

```
口令 → KEK → 加密 file_key
用户改口令 → KEK 变了 → 所有 file_key 无法解密 → 所有附件永久打不开
```

**这是一个必须提前解决的设计缺陷**（消息正文、附件元数据同理）。

权威设计见 [crypto-protocol.md](crypto-protocol.md) §10.2。本节说明它在附件场景下的具体含义。

### 11.2 解决：两层密钥

```
口令 ──argon2id──▶ KEK ──加密──▶ MK（主密钥，32B 随机，永不变）
                                    │
                                    ├──加密──▶ 身份私钥
                                    ├──加密──▶ 消息正文
                                    ├──加密──▶ file_key
                                    └──加密──▶ 文件名等元数据
```

- `MK` 只在首次创建身份时随机生成一次，**此后永不改变**；
- 改口令 → 仅需用新 KEK 重新加密 `MK`（32 字节，瞬时完成）；
- 所有其他数据用 `MK` 加密，**不受改口令影响**。

### 11.3 落盘与解锁流程

```
identity.key   ← 身份私钥，用 MK 加密
wrapped_mk     ← MK，用 KEK 加密
identity.meta  ← 指纹、argon2id 参数（salt, m, t, p）
```

```
解锁：
  口令 → argon2id(meta 中的参数) → KEK
  KEK 解密 wrapped_mk → MK
  MK 解密 identity.key → 私钥
```

**安全说明**：MK 驻留内存期间，任何能读内存的恶意进程都能获得它。这与"用 KEK 直接加密"相比**没有降低安全性**（KEK 同样在内存中），只是把"长期数据"与"口令"解耦了。

### 11.4 对现有文档的影响

这要求修改 [crypto-protocol.md](crypto-protocol.md) §10 的密钥存储设计。已在那边同步更新。

## 12. 内存与流控

**恒定内存**，与文件大小无关：

```
发送：读一块(64 KiB) → 加密 → 入队 → 释放 → 读下一块
接收：收一块 → 解密 → 写盘 → 释放 → 收下一块
```

- 使用 `io.Reader` / `io.Writer` 流水线，**禁止** `os.ReadFile` 整个文件；
- `file_hash` 用 `hash.Hash` 流式更新，**不要**缓存整个文件来算哈希；
- 单次传输的峰值内存 ≈ `chunk_size × 队列深度`，可控。

**磁盘检查**：接收方在 `FILE_ACCEPT` 前检查可用空间，**必须留有余量**（建议要求 `可用空间 > size × 1.1`），避免收一半磁盘满。

## 13. 安全考虑

| 风险 | 防护 | 状态 |
|---|---|---|
| 文件名泄露 | 传输自动加密（在 SECURE 帧内）；本地用 MK 加密 | ✅ |
| 路径穿越 | 存盘路径用 `file_id`，原始文件名仅显示 | ✅ |
| 截断 | `total_chunks` + `is_final` 标志 + `file_hash` | ✅ |
| 块重排 | `index` 进 nonce 与 AAD | ✅ |
| 块重放 | 接收方位图去重 + 会话级重放窗口 | ✅ |
| 磁盘耗尽（DoS） | 接受前检查空间 + 大小上限 + 配额 | ✅ |
| 超大文件 | 可配置上限（建议默认 100 MB，可调） | ✅ |
| 仅中继可达时的大文件 | 拒绝 + 提示（[nat-traversal.md](nat-traversal.md) §9.2） | ⚠️ 需产品决策 |
| 恶意文件内容（病毒、木马） | **不做扫描** | ❌ 见下 |
| 文件大小元数据泄露 | 传输量本身暴露大小 | ❌ 已知局限 |
| MIME 欺骗 | MIME 由发送方声明，不可信 | ⚠️ UI 不应据此自动执行/打开 |

### 13.1 关于恶意文件

**本项目不做病毒扫描**，也**不应**在文档或 UI 中暗示文件是安全的。

UI 应做到：

- 明确显示发送者身份与**信任状态**；
- 打开文件的动作**交给操作系统**（用系统默认程序打开），不在应用内执行任何内容；
- 提示"来自未验证联系人的文件存在风险"。

### 13.2 关于 MIME 与自动打开

**绝不要**根据对端声明的 MIME 类型自动打开或预览文件——MIME 是攻击者可控的输入。图片预览应基于**实际解码结果**（解码失败则不预览），而非声明的 MIME。

## 14. UI 设计

### 14.1 消息流中的附件卡片

```
┌─────────────────────────────────┐
│ 📎 report.pdf                   │
│    2.4 MB                       │
│    [========>        ] 62%      │
│    1.5 MB/s · 剩余 1 秒          │

```

- 完成后：`[打开] [另存为] [显示所在位置]`
- 失败：显示原因 + `[重试]`
- 未验证联系人发来的文件：卡片上带**警告标记**

### 14.2 拖放与粘贴（桌面）

- 拖文件到窗口 → 发起 `FILE_OFFER`；
- 粘贴图片 → 可选择以附件发送（不要自动发送——粘贴可能含敏感截图）。

### 14.3 图片预览

- 收齐**并验证** `file_hash` 后才生成预览；
- 预览基于实际解码（§13.2）；
- 大图解码可能占用大量内存，需限制预览尺寸（如解码时按需缩放，或用 `image.Decode` + 尺寸检查拒绝超大图）。

### 14.4 移动端

- 需要平台文件选择器（Gio 不提供，需平台集成）；
- 需要处理"文件访问权限"与"分享"意图。

> **不确定项**：Gio 在 Android/iOS 上访问系统文件选择器的具体方式需在实现时验证（可能需通过平台宿主代码桥接，类似 [transport-lan.md](transport-lan.md) §9.1 的 MulticastLock 问题）。

## 15. 测试要点

### 15.1 密码学正确性

| 用例 | 期望 |
|---|---|
| 单块文件（size < chunk_size） | 正常，且该块 `is_final = 1` |
| 恰好整除 chunk_size 的文件 | 块数计算正确，末块带 final |
| 空文件（0 字节） | 明确定义行为（建议：允许，1 个空块） |
| **重排两块** | 解密失败或 `file_hash` 不匹配 |
| **丢弃尾部块** | 因缺 `is_final` 块 / 块不齐而拒绝 |
| **丢弃中间块** | 块不齐，不完成 |
| **重复投递同一块** | 第二次被拒绝并计数 |
| 篡改任一块密文 | 该块解密失败 |
| 篡改 `index` | 解密失败（nonce 不匹配） |
| `file_hash` 不匹配 | 拒绝，标记失败 |
| 用错误的 `file_key` | 全部解密失败 |

### 15.2 行为测试

| 场景 | 期望 |
|---|---|
| 传输中连接断开 | 明确失败（首期）；标记可重试 |
| 传输中取消 | 双方清理，位图删除 |
| 磁盘空间不足 | `FILE_REJECT(reason=磁盘空间不足)`，不开始传 |
| 超过大小上限 | 同上 |
| 传 1 GB 文件时的内存占用 | 恒定，不随文件增长 |
| 传大文件时发聊天消息 | 延迟 ≤ 约一个块的传输时间 |
| 传大文件时的 CPU 占用 | 主要是 SHA-256，可接受 |
| 对端为 `BLOCKED` | 拒绝 |

### 15.3 资源测试

- 长时间传输（如 1 小时）无内存增长；
- 令牌桶限速生效（实测速率不超过配置值）；
- 队列满时正确背压，不丢块、不死锁。

## 17. 一句话总结

> **64 KiB 分块 + index 进 nonce/AAD + 末块 final 标志 + 整体 file_hash**，解决重排/截断/重放；
> **独立 `file_key` + 主密钥 MK 分层**，解决续传、转发与改口令；
> **两级优先队列 + 令牌桶**，让附件不阻塞聊天；
> **路径只用 file_id、不扫毒、不按 MIME 自动打开**，划清安全边界。
