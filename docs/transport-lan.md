# 局域网传输层设计

> 首期范围：**局域网（同一广播域）内的 mDNS 发现 + TCP 直连**。
> 公网穿透（打洞 / 中继）不在首期，但接口已预留，见 §8。

## 1. 范围与前提

**成立的前提**：
- 双方处于同一局域网（同一 WiFi / 同一交换机），mDNS 组播可达；
- 双方之间无 ACL 阻止点对点 TCP 连接。

**不成立时**：发现失败或连接失败。UI 必须给出可诊断的提示（"未在局域网内发现对方""连接被拒绝"），而不是无限转圈。

---

## 2. 拓扑

```
        ┌──────────── 局域网 ────────────┐
        │                                │
   ┌────▼────┐   mDNS 组播 (UDP 5353)   ┌────▼────┐
   │  设备 A │◀────────────────────────▶│  设备 B │
   │         │                          │         │
   │ TCP :P  │◀────── TCP 长连接 ───────▶│ TCP :P  │
   └─────────┘      (E2EE over TLS-less)└─────────┘
```

- **mDNS**：仅用于发现与交换元数据（指纹、端口、协议版本）。
- **TCP**：承载所有帧。**不启用 TLS**——E2EE 已在应用层完成，再加 TLS 是冗余的，且会引入证书管理负担。
  - 但这意味着帧头（`SessionID`、`Epoch`、`Seq`）在链路上明文可见。见 [wire-protocol.md](wire-protocol.md) §3.2 的讨论。
  - 局域网内被动嗅探者能看到"两台设备在通信"以及消息**数量**与**时序**，但看不到内容。这与 [threat-model.md](threat-model.md) 的元数据声明一致。

## 3. 服务发现（mDNS）

### 3.1 服务类型

```
服务类型: _keytalk._tcp.local.
实例名:   <display-name>._keytalk._tcp.local.    （仅展示用，不可信）
端口:     监听端口（见 §4）
TXT 记录: fp=<指纹 hex>
          v=1
          n=<display-name, 可选>
```

- 端口建议由系统分配（`:0`）后注册，避免固定端口冲突；也可配置固定端口，便于排查。
- **TXT 中的指纹不可信**：任何人都能广播任意指纹。它只作为"索引/提示"，**真正的身份确认必须来自 E2EE 握手**（[crypto-protocol.md](crypto-protocol.md) §6.4）。
  - 攻击者可广播**他人指纹**来诱导连接。因此：**连接后必须校验握手得到的指纹与预期一致**；若与联系人表不符，立即断开并告警。
- `Instance` 名与 `n=` 字段均为**纯展示**，需做转义与长度限制，UI 展示时视为不可信输入（防注入、防超长字符串撑破布局）。

### 3.2 mDNS 库选型

候选（实现前**必须核对各自最新维护状态与 Go 1.25 兼容性**，不要盲选）：

| 库 | 说明 |
|---|---|
| `github.com/hashicorp/mdns` | 接口简单，长期存在；需确认是否仍维护 |
| `github.com/grandcat/zeroconf` | 功能较全（注册+浏览）；需确认维护状态 |
| `github.com/libp2p/zeroconf` | libp2p 使用的 fork；若未来接 libp2p 可平滑 |

**不确定项**：上述库的当前维护活跃度我无法在离线环境核实，请在动手前用 `go list -m -versions` 与实际浏览测试确认。若均不理想，备选方案是直接基于 `golang.org/x/net/ipv4` / `ipv6` 实现最小 mDNS（仅需注册 + 浏览 + TXT 解析，工作量可控但需处理 DNS 报文编码）。

### 3.3 浏览器行为

- 应用启动即开始浏览 `_keytalk._tcp.local.`。
- 发现新实例 → 校验 `fp` 是否在联系人表中 → 命中则触发连接流程。
- **未在联系人表中的实例不自动连接**，仅在 UI 的"发现的设备"列表中展示，由用户决定是否添加。
  - 这避免了对陌生设备的自动握手，也降低了被诱导连接的风险。
- 实例消失（`PeerLost`）→ 标记为离线，但**不删除**联系人。

### 3.4 多网卡

设备常有多个接口（WiFi / 以太网 / VPN / Docker bridge）。mDNS 必须：

- 在所有**支持组播**的接口上注册与浏览；
- 排除回环与明显无关的虚拟接口（可配置）；
- 若只在默认路由接口上操作，会导致"连了 VPN 就发现不到"的经典问题。

**实现提示**：枚举 `net.Interfaces()`，过滤 `FlagUp && FlagMulticast`，对每个接口分别建立 mDNS 实例。

## 4. TCP 监听与连接

### 4.1 监听

```go
ln, err := net.Listen("tcp", fmt.Sprintf(":%d", port))
```

- 监听所有接口（`0.0.0.0` / `::`）。
- 端口若为 `0`，从 `ln.Addr()` 取实际端口，再用于 mDNS 注册。
  - **注意顺序**：必须先 `Listen` 拿到端口，再注册 mDNS。

### 4.2 入站连接的对端识别

TCP 层无法直接得知对端指纹，必须：

1. 接受连接；
2. 等待对端发送 `KEM_INIT`（或主动发送 `KEM_INIT`，取决于 §6 的角色规则）；
3. 从握手结果中获知对端指纹；
4. 在此之前，连接处于"未识别"状态，需**限制资源**（见 §4.3）。

**防御要点**：

- 未识别连接同样要有**握手超时**（建议 10s），超时关闭；
- 限制**并发未识别连接数**（建议 8），防止连接耗尽；
- 来自不在 mDNS 发现列表中的地址的连接：允许（对方可能先发现我方），但同样受上述限制。

### 4.3 连接池

```go
type peerConn struct {
    fp     string          // 对端指纹（握手后填充）
    conn   net.Conn
    sendQ  chan []byte     // 有界队列
    sess   *crypto.Session
    state  atomic.Value
}
```

| 约束 | 值 | 理由 |
|---|---|---|
| 每 peer 连接数 | 1 | 去重规则见 [wire-protocol.md](wire-protocol.md) §8.2 |
| 发送队列长度 | 256 帧 | 有界，防内存膨胀 |
| 队列满时 | 返回"背压"错误给 core，**不阻塞** | 阻塞会导致整个事件循环卡住 |
| 读缓冲 | 64 KiB | 与 `MaxFrame` 匹配 |

**背压处理**：`Send` 在队列满时立即返回错误，由 core 决定是丢弃、排队到磁盘、还是提示用户。**绝不**通过阻塞等待来"解决"队列满——那会级联阻塞网络 goroutine。

## 5. 心跳与重连

### 5.1 心跳

- 空闲超过 **30s** 发送 `PING`；
- 收到 `PING` 回 `PONG`；
- 连续 **3 次**心跳无响应（约 90s）→ 判定连接死亡，关闭并触发重连。
- `PING`/`PONG` 均走 AEAD 加密（见 [wire-protocol.md](wire-protocol.md) §2.1），因此心跳本身也能隐式验证密钥同步状态。

### 5.2 重连退避

```
第 n 次重连延迟 = min(2^n 秒, 60 秒) + 随机抖动(0~1s)
n 在连接成功后重置为 0
```

- **必须加抖动**，否则多设备同时断网后会同步重连，形成惊群。
- 重连后**必须重新走完整握手**，不复用旧会话密钥。
  - 理由：连接中断可能意味着中间人介入，重新握手可重新认证。
  - 代价：每次重连都有一次 OpenPGP 运算（若用硬件密钥需插卡）。若这成为体验问题，可考虑"短时断线重连复用会话"——但那需要额外设计（如基于旧会话密钥的快速恢复协议），**首期不做**。

### 5.3 TCP keepalive

同时启用 TCP 层 keepalive（`net.TCPConn.SetKeepAlive(true)`）作为兜底，处理对端主机断电等无 FIN 的场景。但**应用层心跳才是权威**，TCP keepalive 仅辅助。

## 6. 与协议层的角色分工

传输层**不参与**握手角色决策，只负责搬运字节。但连接去重需要指纹，而指纹只有握手后才知道：

```
1. TCP 连接建立（可能双向同时建立 → 两条连接）
2. 双方按 [wire-protocol.md](wire-protocol.md) §8.2 规则基于「已知的对端指纹」决定角色
   └─ 指纹来自 mDNS TXT（提示）+ 联系人表（权威）
3. initiator 发 KEM_INIT
4. responder 收到后校验指纹是否与 mDNS 声明一致
   ├─ 不一致 → 断开（可能是 mDNS 欺骗）
   └─ 一致   → 继续握手
5. 握手完成后，若发现存在重复连接，按 wire-protocol §8.2 规则关闭多余连接
```

**这个流程有一个固有窗口**：在握手完成前，无法用密码学方式确认对端身份。因此：

- 握手前**不得**基于 mDNS 的指纹做任何授权决策；
- 握手前**不得**显示"已连接到 Alice"这类确定性文案，应显示"正在验证…"。

## 7. 离线消息（首期不做）

### 7.1 问题

纯 P2P 的无解约束：**双方必须同时在线**。A 在 B 离线时发送的消息无法投递。

### 7.2 可选方案（均为二期及以后）

| 方案 | 性质 | 代价 |
|---|---|---|
| Store-and-forward 中继 | 引入服务器（可只存密文） | 需部署与运维；隐私模型变化（元数据暴露给中继） |
| 局域网内其他在线设备缓存 | 仍是 P2P，但需信任第三方设备 | 复杂度高；设备可能不可信 |
| 明确不支持离线 | 最简 | 用户预期管理 |

**首期决策：明确不支持，并在 UI 中如实告知**（如联系人离线时禁用输入框并提示"对方离线，消息无法送达"）。

> **不要**做"看起来能发但实际丢失"的假象。发送按钮在对方离线时应禁用，或发送后明确标记为 `failed`。

### 7.3 消息状态

即使在线，也要区分：

```
PENDING  → 已入队，等待对端 RECEIPT
ACKED    → 收到 RECEIPT
FAILED   → 连接断开且未收到 RECEIPT
```

UI 用不同图标区分，用户可见。

## 8. 为公网扩展预留的接口

> **公网的完整设计**（NAT 行为分类、ICE/STUN/TURN、信令与签名、中继成本控制）见 [nat-traversal.md](nat-traversal.md)。本节只说明接口扩展点。

`transport.Transport` 接口（见 [architecture.md](architecture.md) §3.3）已抽象出：

- `Start` / `Close`：生命周期
- `Send(peerID, frame)`：发送
- `Events()`：发现 / 连接 / 数据事件

**未来接入公网时**，新增实现即可：

| 实现 | 技术 | 说明 |
|---|---|---|
| `transport/lan` | mDNS + TCP | 首期 |
| `transport/ice` | pion/webrtc（ICE + DTLS + SCTP DataChannel） | **推荐**，理由见 [nat-traversal.md](nat-traversal.md) §5.2 |
| `transport/libp2p` | go-libp2p（Noise + QUIC + DHT + DCUtR + Relay） | 备选，依赖重 |

**接口需要扩展但首期不必实现的点**（详见 [nat-traversal.md](nat-traversal.md) §10.3）：

- `PeerInfo.Addrs` 已支持多地址（公网需要多个 ICE 候选地址）；
- 需要新增**路径变化事件**（打洞成功、中继→直连升级）；
- 需要新增**连接路径上报**（UI 要能显示当前是直连还是中继）；
- `Send` 的错误语义需要区分"暂时不可达"（可重试）与"永久失败"；
- 需要支持 **ICE restart**（网络切换后重新协商候选）。

**不要为未来过度设计**，但要保证这些扩展点不因首期实现而封死。

## 9. 移动端特有问题（重要，容易踩坑）

桌面端 mDNS 通常开箱即用；**移动端会静默失败**，这是本项目在移动平台上最大的落地风险。

### 9.1 Android

| 问题 | 说明 | 应对 |
|---|---|---|
| **组播被系统过滤** | Android 为省电，默认不接收非定向的组播/广播包。**不获取 `MulticastLock` 就收不到 mDNS 响应**（表现为"能发不能收"）。 | 必须获取 `WifiManager.MulticastLock`，用完释放 |
| Doze / 后台限制 | 后台时网络与 CPU 受限，长连接被断开 | 前台服务（`ForegroundService`）+ 常驻通知；或接受"后台不保活" |
| 网络切换 | WiFi ↔ 蜂窝切换会重建所有接口 | 监听网络变化，重建 mDNS 与监听 |
| 权限 | 需要 `INTERNET`、`ACCESS_NETWORK_STATE`、`ACCESS_WIFI_STATE`、`CHANGE_WIFI_MULTICAST_STATE` | `AndroidManifest.xml` 声明 |

**获取 MulticastLock 的路径**：

Gio 应用的 Android 宿主是 Gradle 工程。获取 lock 需要访问 Java API，可选：

1. 在 Android 宿主的 Java/Kotlin 侧获取 lock 并持有（最简单，但生命期与 Activity 绑定，后台易失效）；
2. 通过 JNI 从 Go 调用（需要 `JavaVM` 指针与 `JNIEnv`，Go 侧用 `golang.org/x/mobile` 或自行封装）；
3. 用 `gomobile bind` 生成一个 Java helper 暴露给 Go。

> **不确定项**：Gio 当前版本是否直接暴露获取 `JavaVM` / `Context` 的 API，我无法离线核实。实现阶段需查阅 `gioui.org/app` 的 Android 相关 API 与 Gio 的示例工程。**这是选型风险点**：如果桥接过于复杂，可能需要放弃 Go 侧发起 mDNS，改由 Java 侧发现后把结果传给 Go。

### 9.2 iOS

| 问题 | 说明 | 应对 |
|---|---|---|
| **本地网络权限** | iOS 14+ 访问本地网络需用户授权，**首次访问会弹窗**；未声明则直接失败 | `Info.plist` 加 `NSLocalNetworkUsageDescription`（说明用途文案） |
| **Bonjour 服务声明** | 使用 mDNS/Bonjour 需在 `Info.plist` 声明服务类型 | `NSBonjourServices` 数组加入 `_keytalk._tcp` |
| 后台限制 | 应用进入后台后 socket 被挂起，无法维持长连接 | 不支持后台接收；或使用有限的 background mode（本项目不适用） |
| 模拟器 | 模拟器与宿主机网络行为不同，mDNS 可能不通 | 用真机测试 |
| 多播权限文案 | 权限弹窗被拒绝后需引导用户到设置中开启 | UI 提供指引 |

**Info.plist 关键片段**：

```xml
<key>NSLocalNetworkUsageDescription</key>
<string>KeyTalk 需要在局域网内发现并连接你的聊天对象。</string>
<key>NSBonjourServices</key>
<array>
    <string>_keytalk._tcp</string>
</array>
```

### 9.3 跨平台结论

**移动端的局域网 P2P 是可行但有明确边界的**：

- ✅ 前台、同一 WiFi、已授权的情况下可以工作；
- ❌ 后台长期在线做不到（iOS 尤其明确）；
- ⚠️ Android 的 MulticastLock 桥接是**待验证的技术风险**，需在实现前做技术验证（spike）。

**建议**：如果移动端是硬需求，**先做一个最小 spike**（Android 上能否从 Gio 应用成功收到 mDNS 响应），验证通过再投入完整实现。见 [roadmap.md](roadmap.md) 阶段 **S0.2**。

## 10. 防火墙与用户提示

- **Windows**：首次监听会触发 Windows Defender 防火墙弹窗。若用户拒绝，入站连接全部失败。
  - UI 应能检测到"监听成功但从未收到过任何入站连接"这一模式，并提示检查防火墙。
- **macOS**：同样有应用防火墙；还需注意 macOS 15+ 的本地网络权限类似 iOS。
- **Linux**：通常无防火墙，但 `ufw`/`firewalld` 可能阻止。

**用户提示文案**必须在连接失败时给出**可操作**的建议（检查防火墙、确认同一 WiFi、确认对方在线），而不是"连接失败"。

## 11. 测试要点

| 场景 | 验证 |
|---|---|
| 同机双实例（不同端口） | 能通过 mDNS 互相发现并通信 |
| 两台同 WiFi 设备 | 正常发现、握手、收发 |
| 有 VPN 开启 | 仍能在物理接口上发现（验证 §3.4 多网卡处理） |
| 对端离线后再上线 | 重连退避生效，不刷屏 |
| 拔网线 → 心跳超时 → 恢复 | 正确进入 CLOSED 并重连 |
| 双方同时发起连接 | 去重规则生效，只保留一条 |
| 伪造 mDNS 指纹（广播他人指纹） | 握手校验发现不一致，断开并告警 |
| 大量并发未识别连接 | 受 §4.2 限制，不耗尽资源 |
| 超长/畸形 mDNS TXT 记录 | 不崩溃、不撑破 UI |
| 移动端后台 30 分钟后回前台 | 连接状态正确恢复或重连 |

## 12. 待定问题

| 问题 | 影响 | 建议 |
|---|---|---|
| mDNS 库最终选型 | 依赖稳定性 | 实现前用实际浏览测试验证 |
| Android MulticastLock 桥接方式 | 移动端可行性 | **先做 spike 验证** |
| 固定端口 vs 随机端口 | 可排查性 vs 冲突 | 默认随机，允许配置固定 |
| 是否支持 IPv6-only 网络 | 覆盖 | 监听 `::` 通常兼顾，需实测 |
| 断线后是否复用会话 | 重连体验 vs 安全 | 首期不复用 |
