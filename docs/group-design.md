# 群组设计

> 状态：**设计稿，未实现**。本文只讨论"怎么做、为什么这么做、代价是什么"，
> 不含代码。实现前需要先回答 §8 的开放问题。

## 1. 目标与边界

一个群组是**一群互不信任彼此身份、但都信任发起者**的人。发起者收集成员的
OpenPGP 公钥，生成一把**对称的群组密钥 GK**，把 GK 分别用每个成员的公钥
包一份发给他们。成员用这把 GK 加密/解密群消息。

这是标准的"发送者分发群组密钥"（sender-key）模型，**不是** Signal 的
sender-key-ratchet，也**不是** MLS。后两者解决的是"成员频繁进出 + 前向保密 +
后向保密 + 大规模"的组合问题，代价是复杂的树状密钥结构和状态同步。本工具
面对的是小群、低频率、离线容忍——用 MLS 是拿大炮打蚊子，而且它的状态同步
在"有人长期离线"时的行为很难向用户解释。

**明文边界**：GK 只在内存里、只在群内成员手里。磁盘上没有任何明文 GK。

## 2. 密钥分发（对应你说的"发起者生成对称密钥给全体成员"）

```
发起者 I:
  1. 收集成员公钥 P_1..P_n（含自己）
  2. 生成 GK ← 32 字节随机
  3. 对每个成员 i:  env_i = PGP.Seal(P_i, GK)      # 用对方公钥加密 GK，签名
  4. 把 {group_id, epoch, [env_1..env_n]} 通过已建立的 E2EE 单聊通道
     分别发给每个在线成员
```

- `PGP.Seal` 复用现有的 `PGPProvider.Wrap`（加密 + 内联签名）。成员解开后，
  签名验证"这确实是发起者发的"——否则任何拿到 `env_i` 的人都能冒充发起者
  分发假 GK。
- **每个成员只拿到自己那份 `env_i`**，拿不到别人的。因此一个成员无法
  解密另一个成员的具体分发内容，只能解密 GK。这是最小暴露。
- 需要新增的密码学原语：**没有**。`Wrap` / `Unwrap` 已足够（成员用发起者
  公钥 `AddPeerKey` 后 `Unwrap`）。

## 3. 成员变更与换钥（对应你说的"有人进出就重置一次"）

**每一次成员集合变化都换一把全新的 GK，epoch 加一。** 并且：

- **退出**：换钥后，新 GK **不发给退出者**。他此后收到的群消息都是新 epoch，
  没有新 GK → 解不开。
- **加入**：新成员拿到的 GK 就是当前 epoch 的。他**看不到加入之前的历史**——
  因为历史消息是用旧 GK 加密的，他没有旧 GK。

> ⚠️ **必须诚实告诉用户的两件事**，否则是安全误导：
> 1. 退出者**仍然能解密他在退出前收到的所有历史消息**。sender-key 模型
>    做不到"收回已发出的秘密"。换钥只保证"此后"的保密。要收回历史，只能
>    换钥后**重发**全部历史（成本高，且旧密文若已被保存无济于事）。
> 2. 若退出者保存了某条旧 epoch 的消息密文，换钥不影响他解它。
>
> 这是设计的天花板，不是实现缺陷。文档与 UI 都必须写清楚，不能让人以为
> "踢人 = 他什么都看不到了"。

**换钥的拓扑**：发起者重新走一遍 §2 的分发，只发给**当前**成员集合。这是
O(n) 次 Wrap，小群没问题；n 大时要考虑批量。

## 4. 发送者身份：群消息也要能验签

群消息用 GK 做 AEAD（ChaCha20-Poly1305）加密。但 AEAD 只保证"这条消息来自
**某个持有 GK 的人**"，不保证"来自声称的那个人"——群内任何成员都能伪造
"这是 Alice 说的"。

因此每条群消息必须**额外签名**：

```
group_msg = { group_id, epoch, sender_fp, ts, aead(GK, body), sig_by_sender }
```

接收方用一个**独立的 detached 签名**（`Sign` / `VerifyPGP`，用发送者公钥）
验证"这确实是 sender_fp 发的"。发送者公钥来自通讯录（带外核对过），
**不能**信任消息里自带的公钥。

> 代价：每条群消息要验一次签名。小群可接受。大群要用 Merkle / 批量验签，
> 超出本期范围。

## 5. 离线与"信息能写库、暂时看不了"（对应你最后那段）

这是这套设计里最容易做错、也最容易向用户说错的部分。

### 5.1 你的需求拆成两件事

1. **成员暂时拿不到 GK 时，群消息照常到达、照常落库**——不能因为"还没钥匙"
   就把消息丢了。
2. **拿到 GK 之前，界面显示"暂不可读"，而不是显示乱码或空白**。

### 5.2 关键洞察：密文可以存，明文绝不能留

群消息到达时，接收方持有的是 **AEAD 密文**。此时有两种存法：

- **存密文**（推荐）：把 `{group_id, epoch, ct, nonce, sender_fp, sig}` 原样
  写进库。等 GK 到手，再解密。**这是"信息依旧可以写入数据库，只是暂时无法
  查看"的正确实现**——库里存的就是密文，本来就不需要 GK 才能存。
- ~~存明文~~：需要先解密，而解密需要 GK。拿不到 GK 就存不了明文。所以如果真的
  "暂时看不到"，那它必然是以密文形态存的。这一点必须想清楚：**"能写库"和
  "看不到"之所以能同时成立，正是因为库里存的是密文。**

### 5.3 epoch 是这里的关键

消息按 epoch 分筒。接收方可能只有 epoch 3 的 GK，却收到了 epoch 4 的消息
（换钥期间掉线）。处理：

```
收到群消息 m:
  先把 m 的密文落库（无论有没有 GK），状态 = unreadable
  若 m.epoch 的 GK 在手上 → 立刻解密，状态改 readable
  否则 → 保持 unreadable，UI 显示"等待群组密钥（epoch N）"
```

**绝不允许**用错误 epoch 的 GK 去解另一 epoch 的密文。AEAD 会失败，但不能把
"AEAD 失败"当成"消息损坏"——它是正常的"epoch 不匹配"。因此 AAD 里必须绑定
`group_id ‖ epoch`，解错了直接失败，不会解出垃圾。

### 5.4 等待发起者在线

发起者是唯一持有 GK 明文的人。成员 A 离线错过了换钥，重新上线后需要向发起者
（或任一在线的、已持有新 GK 的成员）**索取**该 epoch 的 GK：

```
成员上线 → 发现自己库里有 epoch 4 的 unreadable 消息，但只有 epoch 3 的 GK
        → 向发起者发 GROUP_KEY_REQUEST{group_id, epoch 4}
发起者在线 → 回 GROUP_KEY_DELIVERY{env_A for epoch 4}
        → 成员解开、落库、触发"重扫 unreadable 消息 → 能解的改 readable"
```

- 索取走已有的 E2EE 单聊通道，不需要新传输。
- **发起者不在线就一直等**——这正是你说的"需等待发起者在线时同步密钥"。
  界面应显示"等待发起者上线补发密钥（epoch N）"，而不是一个转圈。
- 谁来满足请求？最稳妥是**只信任发起者**（以及发起者授权的转发者）。让任意
  成员转发 GK 扩大了信任面，需要它同时证明"这把 GK 确实属于 epoch N 且没被
  篡改"——用发起者对 `{group_id, epoch, GK_hash}` 的签名即可，但增加复杂度。
  **本期建议：只由发起者回应**，简单、信任面最小。

## 6. 与现有分层的挂接点

- `internal/crypto`：新增纯函数 `WrapGroupKey` / 无（复用 `Wrap`/`Unwrap`）。
  实际只需一个把 `[]env` 编解码的 helper。**不引入新原语**。
- `internal/group`（新包）：群组状态——成员表、epoch、当前 GK（内存）、
  换钥、消息入队/解密。纯逻辑，可单测，不碰网络。
- `internal/db`：新增 `groups` 表（成员、epoch）与群消息列（`group_id`,
  `epoch`, `ct`, `nonce`, `sig`, `readable`）。**密文列就是现有 attach/消息
  加密思路的延伸**。
- `internal/session`：新增 `GROUP_KEY_DELIVERY` / `GROUP_KEY_REQUEST` 帧类型，
  跑在现有 E2EE 会话上。
- `internal/ui`：群会话视图、成员管理、"等待密钥"状态、epoch 切换提示。

## 7. 存储与 UI 状态机（"暂时看不了"到底长什么样）

群消息在库里的状态：

| 状态 | 含义 | 界面 |
|---|---|---|
| `readable` | 已用正确 epoch 的 GK 解密 | 正常气泡 |
| `unreadable` | 有密文，缺该 epoch 的 GK | 灰色占位"等待群组密钥（epoch N）"，**不显示任何正文** |
| `tampered` | 有 GK 但 AEAD 校验失败 | 红色"消息校验失败（可能被篡改）"，**不静默丢弃** |

`unreadable` → `readable` 的迁移在**每次拿到新 GK 时**触发一次全库重扫。
这是 O(该 epoch 的消息数)，可接受；大群需索引 `(group_id, epoch, readable)`。

> 绝不允许"因为解不开就删掉"。解不开的消息是证据，删了等于帮攻击者擦痕迹。
> 也绝不允许显示乱码冒充正文——用户会以为是编码问题，而实际是密钥问题。

## 8. 开放问题（实现前必须定）

1. **发起者单点**：发起者长期离线，群就换不了钥、新成员进不来。要不要支持
   "发起者授权多个密钥分发者"？——增加可信度链复杂度，本期建议不做，但要在
   UI 里说清"群主的在线状态决定群的可管理性"。
2. **退出者的历史**：见 §3 警告。是否提供"换钥后重发历史"选项？成本与收益
   需要产品决策。
3. **重放与乱序**：群消息需要单调序号还是仅靠时间戳？（单聊已有重放窗口，
   群聊要复用还是新做？）
4. **成员公钥的可信**：发起者收集成员公钥时，是"随便谁递公钥都收"还是
   "必须和成员各自带外核对指纹"？后者安全但流程重。建议：发起者至少和每个
   成员核对指纹，否则群内任何人都能被中间人冒充。
5. **群大小上限**：Wrap 是 O(n)，验签是每条消息 O(1) 但每次换钥 O(n)。
   建议明确"本工具面向 ≤ 几十人的群"，超过就不承诺性能。

## 9. 为什么不做别的东西（免得日后有人问）

- **不做 MLS**：见 §1。状态同步在长期离线场景下无解地复杂。
- **不做 sender-key ratchet**：每一轮的棘轮状态必须严格同步，掉一个成员就
  全网卡住；而本工具明确要容忍离线。
- **不做"服务端代发"**：没有服务器是产品前提。
- **不在群里传私钥**：GK 是对称密钥，**不是**身份私钥。任何设计里私钥都不
  出本机——这条红线不因群组功能松动。
