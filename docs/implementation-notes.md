# 实现笔记：传输层与会话层

本文记录 S4/S5 阶段的实现决策，重点是**踩过的坑**——那些设计文档里
写不出来、只有真跑起来才会暴露的问题。

设计意图见 [architecture.md](architecture.md) 与 [wire-protocol.md](wire-protocol.md)；
本文只记录"为什么代码长这样"。

---

## 1. 分层与依赖方向

```
cmd/keytalk ──► session ──► crypto
                  │          wire
                  └────────► transport/lan
```

硬性约束（用户明确要求低耦合，这些不是建议）：

| 规则 | 原因 |
|---|---|
| `crypto` **不导入任何内部包** | 它是纯密码学层，可独立审计、独立复用 |
| `wire` 是纯函数，不导入任何内部包 | 编解码无状态，方便 fuzz |
| **`transport` 不得导入 `crypto`** | 未来中继节点会复用传输层，而中继**绝不能接触密钥材料**。物理上禁止导入，比写文档约束可靠 |
| `session` 是**唯一**同时导入 crypto+wire+transport 的包 | 组装逻辑集中在一处，便于审查 |
| `ui` 不得直接调用 transport/crypto/files | 全部经 `core`，保证 UI 线程不阻塞 |

`transport` 也不导入 `wire`：`transport.MaxFrameSize`（1 MiB）与
`wire.MaxFrame` 靠一个**测试守卫**（`TestMaxFrameSizeContract`）保持一致，
而不是靠 import。这样换了编码方案也不牵动传输层。

## 2. 传输层的两个关键设计

### 2.1 入站连接一律视为未知来源 ← 有安全含义

**这是本项目发现的最严重缺陷，值得完整记录。**

最初 `handleInbound` 按**来源 IP** 把入站连接匹配到已知对端，理由是
"对方的 mDNS 记录说它在这个 IP 上"。看起来很自然，实际是错的：

```
攻击者（同机任意进程，或同一 NAT 后的任意设备）
  → 连上你的 TCP 端口（源 IP 与真实对端相同）
  → 传输层认为"这就是对端"，用新连接**顶替**旧连接
  → 旧连接被关闭 → 真实会话被摧毁
```

攻击者**不需要任何密钥、任何密码学能力**，只要能从同一个 IP 发起
TCP 连接，就能反复打断会话。实测复现：

```
[bob] transport.ConnClosed {ID:AAAA Err:transport: frame too large: declared 4294967295 > 1048576}
```

（攻击者连上后立刻发一个畸形长度就断，真实对端的连接被连带关闭。）

**修复**：入站连接永远标记为未知来源（临时 ID `inbound:<addr>`），
只有**应用层握手验签成功**后，才通过 `AdoptConnection(tempID, realID)`
把连接归属到真实身份。

核心原则：

> **IP 是信封，不是身份。** 身份只能由密码学证明来确立。

这也是为什么 `transport` 层不认识"身份"这个概念——它只认识
"这条连接现在归属哪个 ID"，而 ID 的**可信度**由上层负责。

### 2.2 帧长度必须在分配前校验

`readFrame` 读到 4 字节长度前缀后，**先校验再分配**：

```go
if n > MaxFrameSize { return ErrFrameTooLarge }
if n == 0 { ... }
buf := make([]byte, n)
```

若直接 `make([]byte, declaredLen)`，一个 8 字节的报文
（`0xFFFFFFFF`）就能让服务端尝试分配 4 GiB。

注意这是**传输层自己的** 4 字节前缀，与 `wire` 的帧头无关。
测试里必须绕过 `Send` 直接写原始 TCP 字节——恶意对端不会用我们的 API。
（这个测试最初写错了，验证的是 wire 的长度而不是 transport 的。）

### 2.3 背压是**故意**的

`enqueue` 在队列满时立即返回错误，而不是阻塞或无限增长。
测试里表现为"50 条只发出 47 条"——这是**设计正确**的表现。
无限队列会让慢速对端把内存吃光；阻塞会让 UI 卡死。
正确的做法是把背压暴露给上层，由它决定降级策略。

## 3. mDNS：四个真机上才会遇到的坑

这些在单元测试里**全都测不出来**，只有多进程真机运行才会暴露。

### 3.1 端口 5353 必然被占用

mDNS 规范要求从 5353 收发。但同机通常已经有别的进程占着它
（Windows 的 Bonjour/Dnscache、Linux 的 Avahi、或者**你自己的第二个实例**）。

没有 `SO_REUSEADDR` 时第二个进程直接 `EADDRINUSE`，发现功能完全失效。

修复：`internal/transport/lan/reuse_windows.go` / `reuse_unix.go`。

| 平台 | 需要的选项 | 说明 |
|---|---|---|
| Windows | `SO_REUSEADDR` | Windows **没有** `SO_REUSEPORT`；其 `SO_REUSEADDR` 语义等价于 Unix 的 `SO_REUSEPORT` |
| Unix | `SO_REUSEADDR` + `SO_REUSEPORT` | **两个都要**。只设前者不足以让第二个进程收到组播 |

RFC 6762 §15.1 明确讨论了多进程共享 5353 的情形。

### 3.2 `SetMulticastInterface` 是有状态的

```go
// ❌ 错误：循环结束后只有最后一个接口生效
for _, ifi := range interfaces {
    conn.JoinGroup(ifi, gaddr)
    conn.SetMulticastInterface(ifi)
}
```

多网卡机器上（本机有 WLAN + VMware + WSL + VPN 共十余个接口），
宣告会被发到**最后一个**接口——通常是虚拟网卡，真实局域网上的对端收不到。

表现为"发现静默失败"：没有报错，就是永远发现不了。

**修复**：每个接口各建一个 socket（`mdnsSocket`），
各自 `JoinGroup` + 绑定到自己的接口，发送时逐接口各发一次。

另外：组播**不跨接口**，所以必须逐接口发送，只发一次不行。

### 3.3 不能用来源 IP 过滤自己

早期实现里 `isSelf(srcIP)` 丢弃所有来自本机 IP 的组播，防止自己发现自己。
看似合理，但会连带屏蔽**同一台机器上的另一个 KeyTalk 实例**——
而同机多用户、或本机双实例联调，都是完全合法的场景
（本项目方案 B 的端到端验证正依赖后者）。

**修复**：按**指纹**（报文内容）过滤，不是按 IP（信封）。
再次印证 §2.1 的原则。

### 3.4 多候选地址必须累积

同一次宣告会从每个接口各到达一次，来源 IP 各不相同。若只保留最后到达的，
很可能选中不可路由的虚拟网卡地址（如 `172.22.x` 的 WSL 网段），连接必然失败。

**修复**：`PeerInfo.Addrs` 累积**全部**候选地址，`connFor` 逐个尝试。
这与 [nat-traversal.md](nat-traversal.md) §10.3 "Addrs 支持多地址"的设计一致。

同时，`PeerFound` 事件必须在**地址集合变化**时再次上报——
否则上层只拿到第一个（可能不可用的）地址，后续更可用的地址永远到不了它。

## 4. 会话层的设计

### 4.1 身份识别的"先有鸡还是先有蛋"

入站 KEM_INIT 是加密的，但解密需要知道**发送方**是谁（用谁的公钥验证签名）。
而发送方身份恰恰是我们要确定的。

**错误做法**：信任报文里自称的指纹去查公钥。那样任何人都能自称是别人。

**正确做法**（`identifySender`）：遍历**本地联系人列表**，
逐个注册其公钥并尝试验签，只有当签名验证通过、且指纹与某个联系人匹配时才接受。

> 永远不信任载荷自述的身份，只信任本地联系人表 + 密码学验证。

这个顺序很关键，写反了就是一个完整的身份伪造漏洞。

### 4.2 未知身份必须**静默丢弃**

协议上没有"我解不开你的消息"这种回应。回应会告诉攻击者
"这个指纹/公钥是有效的（或无效的）"，成为一个预言机。

但这带来一个**用户体验问题**：

> 发起方永远等不到响应，界面无限显示"正在握手"。

这是"静默失败"的典型案例，违反了"失败必须浮出水面"的要求。

**修复**：发起方 20 秒超时（`ErrHandshakeTimeout`），
把"对端没有回应"转换成用户可见的事实。

> 协议层静默（防信息泄露）+ 应用层超时（防无声挂起）——
> 这两个要求不矛盾，但必须分别处理。

### 4.3 AAD 必须与方向无关

帧的 AAD 只绑定 `ver ‖ type ‖ sid ‖ epoch ‖ seq`，**不含方向标签**。

方向隔离由**密钥**提供（`key_i2r` / `key_r2i` 是两把独立的密钥），
不需要也不应该在 AAD 里再区分方向。

踩坑记录：测试最初用了 `"i2r"`/`"r2i"` 两个方向的 AAD 标签，
结果收方计算出的 AAD 与发方不同，解密必然失败
（`crypto: decryption failed`）。AAD 是**双方必须算出同一份**的数据。

### 4.4 mDNS 的 `fp` 字段是不可信输入

`PeerInfo.Fingerprint` 来自 mDNS TXT 记录，**任何人都能伪造**。
它的唯一用途是"快速匹配本地联系人表"。

**它不是身份**。真正的身份确立只发生在握手验签之后
（`session.PeerID` 与 `transport.PeerID` 是不同类型，刻意不通用，
避免误把前者当后者用）。

### 4.5 事件通道是**单消费者**资源 ← 本项目最难查的 bug

`session.Manager` 会独占消费 `transport.Events()`。
若上层（例如 CLI）**也**起一个 goroutine 读同一个通道，两者会竞争：
谁先拿到事件是随机的。

实测后果：约一半的帧被 CLI 这个"旁观者"吃掉，会话永远收不到。

症状极具误导性：

```
[bob]  lan: read 771 bytes from inbound:172.22.208.1:62818   ← 传输层收到了
[bob]  (session 层完全没有反应，没有任何日志)                  ← 帧去哪了？
```

排查过程走了很长的弯路，因为它看起来像传输层丢包，
实际是**上层把帧抢走了**。

**修复**：CLI 不再消费传输层事件；在线状态改为低频**轮询**
只读快照 `Transport.Peers()`（1 秒一次，只影响"谁在线"的显示）。

> 教训：想同时观察一个通道，必须由持有者转发（fan-out），
> 而不是各自去读。这个坑在测试代码里也出现过一次
> （见 §5.1），当时只修了测试，没有检查生产代码路径——
> 因此同一个 bug 在生产路径上又活了一轮。

#### 4.5.1 它又发生了一次（第三次），这次在 `core`

写 `internal/core` 时，我再次起了一个 goroutine 去读
`transport.Events()`，**并且在那个函数上方写了一段注释
声称本包是"唯一消费者"**。注释是错的——`session.Manager`
一直在读同一个通道。

这次的症状和第一次一模一样，也照样具有误导性：

```
[bob]  session: sent KEM_INIT to 4AB5BACA...
[bob]  lan: read 192 bytes on 4AB5BACA...        ← 传输层读到了 ACK
[bob]  (session 层没有 rx type=0x02)              ← 帧被偷了
[bob]  session: handshake timed out
```

**为什么反复踩**：这个约束是隐式的，只存在于"人记得不要读"。
因此现在把它**写进接口契约**（`transport.Transport` 的文档注释）：
`Events()` 有且只能有一个消费者，其他组件一律用 `Peers()` 轮询。
把规则放在签名旁边，比放在某一份文档里更不容易被忽略。

这次还改了 `Peers()` 的返回类型（`map` → 有序 `[]PeerInfo`），
使它成为一个真正的公共观察接口，而不是 `lan` 包的内部附加方法。

### 4.6 必须分角色发起连接 ← 多网卡环境下的致命问题

若双方在发现对方后**都**主动连接，会产生两条 TCP 连接（A→B 与 B→A）。
在多网卡机器上（本机有 WLAN/VMware/WSL/VPN 共十余个接口），
两条连接可能走**不同的网卡**：

```
A 从 WSL 网卡（172.22.x）连到 B
B 却在 VMware 网卡（169.254.x）上收到入站
→ B 的应答发到另一条路径，A 永远收不到
```

症状：**随机**握手超时，且取决于哪张网卡先响应——
本机实测 10 次里失败 6~7 次。

**修复**：分角色。规则是"指纹较大的一方主动连接，较小的一方被动等待"。
这是确定性的（两侧比较同一对指纹，结论必然相反），
因此只会产生**一条**连接。

规则方向与会话层的 glare 平局规则一致，避免两层判断错位。

### 4.7 IPv6 zone 标识会破坏 peerID

Windows 上链路本地 IPv6 的 `RemoteAddr()` 会带**接口名**作 zone：

```
169.254.201.140%VMware Network Adapter VMnet8:62733
```

这里面有空格和中文。它被当作 `peerID` 使用，而 peerID 是事件路由的键——
解析、比较、日志都可能被它搞坏。实测表现为"帧收到了却无法路由"。

**修复**：`stripZone` 在构造 peerID 前剥掉 zone。
zone 对**本机**有意义（决定走哪张网卡），但对"这条连接是谁"没有意义。

### 4.8 优先选 IPv4 地址

mDNS 宣告可能带来 IPv6 链路本地地址（`fe80::...`），它们有两个问题：

1. 需要 scope/zone 才能路由，跨机器时 zone 名常常对不上；
2. 即使连上，对端看到的入站可能是**另一条** TCP 连接（IPv4 那条），
   于是双方对"这是哪条连接"的理解不一致。

**修复**：`connFor` 优先选 IPv4 候选，仅在没有 IPv4 时才用 IPv6
（纯 IPv6 网络仍可用）。

### 4.9 角色规则只在一个入口执行 = 竞态

§4.6 的规则是对的，但 `core` 里有**两个**发起入口：
`handlePeerFound`（发现事件驱动）和 `StartChat`（用户点击驱动）。
最初只有前者执行了角色判断，后者无条件发起。

后果：用户点击联系人的时机若早于发现事件到达，
`StartChat` 会先发出 KEM_INIT，随后 `handlePeerFound`
又按规则决定"本方不该发起"。两侧的状态就分叉了。

**修复**：两个入口都执行同一条规则，且规则来自同一个函数
（`core.shouldInitiate`），不会再次分叉。

> 一般化的教训：**同一个不变量有多个入口时，只要有一个入口漏掉，
> 它就不再是不变量。** 判断逻辑必须收敛到一个函数，
> 并且在每个入口都调用它。

## 5. 测试策略

### 5.1 为什么单测全绿仍然会坏

本项目实际发生过：crypto / wire / transport 三个包单测全绿，
但整条链路完全跑不通（§2.1 的入站归属问题）。

**因此增加了 `internal/e2e`**：把四层串起来跑真实 TCP，
覆盖"协作"而非"单元"。

它验证的不只是功能，还有**安全属性**：

| 验证项 | 守护的性质 |
|---|---|
| 30 条消息严格保序、字节一致 | 序号与 AEAD 正确 |
| 陌生身份接入被拒绝 | 身份校验没有被绕过 |
| 攻击后合法流量不受影响 | 拒绝是"干净"的，没有连带摧毁会话 |
| 双向都报告 `Verified:true` | 双方都真的验了签 |

最后一条尤其重要：**只有发起方验证对端是不够的**，
两侧都必须独立完成验证。

### 5.2 无法自动测的部分

- **真机多网卡发现**：依赖具体网络环境，用 `e2e.ps1` 手动验证
- **跨网段**：mDNS 固有限制（不跨广播域），无法在单机测
- **端口冲突**：需要模拟同机其他 mDNS 服务

结论：自动化测试覆盖逻辑，`e2e.ps1` 覆盖环境。
两者都需要，不能互相替代。

### 5.3 `-race` 必须常开 ← 它抓到的是真问题

回看本项目的竞态修复记录，**没有一个是"良性竞争"**。
每一个都会导致真实的错误行为，其中两个直接损害安全目标：

| 位置 | 竞态内容 | 真实后果 |
|---|---|---|
| `crypto.zero()` | 写包级全局 `escapeSink` | 全局变量**持有了刚被清零的密钥缓冲**，清零带来的"缩短密钥驻留"被抵消 |
| `lan.handleRecord` | 锁外读写 `lastPeerEmit` map | Go 的 map 并发写会直接抛 `concurrent map writes` 崩溃 |
| `lan.connFor` | 解锁后读 `*PeerInfo.Addrs` | 与 `append` 竞争，扩容时可能读到被替换的旧底层数组 |

第一条尤其值得记：它看起来只是"竞争检测器抱怨一个只写不读的变量"，
但那个变量的用途正是"骗过编译器不要优化掉清零"——
为了这个目的而引入一个**全局引用**，等于亲手把密钥留在了可达内存里。
正确做法是 `runtime.KeepAlive(b)`：同样阻止死代码消除，
却不引入任何跨 goroutine 的共享状态，也不延长对象的可达性。

因此：**`go test ./... -race` 属于提交前必跑**，不是可选项。

## 6. glare（同时发起）的真实难度

§4.6 讲的是"必须分角色发起"，那是第一层。第二层是在
**已经同时发起之后**如何收敛，这一层本项目返工了三次。

### 6.1 三种错误收敛方式

| 做法 | 结果 |
|---|---|
| 直接接受对方 INIT，覆盖本地 pending | 本地超时定时器随后触发，把**已建立**的会话报告为失败 |
| 拒绝对方 INIT | 双方互相拒绝，双双超时 |
| 在收到对方 INIT 时也当 responder 并回 ACK | 双方都成了 responder，产生**两条平行会话** |

第三种最难查：握手**显示成功**，但消息发到对方不认的那条链上，
表现为"握手成功但消息收不到"。实测约 **1/6** 概率复现。

### 6.2 为什么"逐帧判断"必然出错

早期实现是：

```go
if hasPending(peer) && losesGlareTieBreak(peer) {
    dropPending(peer)   // 让出，当 responder
}
```

问题在于 `hasPending` 是**逐帧**判定的。对方的 INIT 可能在我们的
pending 建立**之前**就到达——那一刻 `hasPending` 为 false，
于是我们不走让出分支、直接当 responder 并回 ACK。
两边都会这样，于是产生两条平行会话。

**结论：角色判定不能依赖"当前是否处于某个状态"，
必须是一个只由双方身份决定的纯函数。**

### 6.3 现在的规则

```
指纹较大的一方 = initiator（始终）
指纹较小的一方 = responder（始终）
```

- 较小方收到较大方的 INIT → 当 responder，回 ACK，
  并 `dropPending`（**连同取消定时器**）。
- 较大方收到较小方的 INIT，且自己也有 pending →
  **忽略对方的 INIT**，继续等自己那条 INIT 的 ACK。

第二条是修复的关键：较大方**不能**顺手回一个 ACK。
否则会把 `m.active` 覆盖成由对方发起的会话，
而对方（较小方）已经放弃了自己的 pending、正等着我们发起的那条——
双方对"当前是哪条会话"的理解再次分叉。

### 6.4 遗留定时器

让出时必须调用 `dropPending`，它会取消超时定时器。
只删除 pending 而不取消定时器，会导致定时器在会话**已经建立**
之后才触发，把成功的握手报告为 `HandshakeFailed`——
这正是本函数历史上最著名的缺陷。

回归断言因此直接检查 `len(pendingTimers) == 0`，
而不是"睡满 20 秒看有没有失败事件"：前者精确且快（约 2.5s），
后者慢且受负载影响。

```go
// 验证规则本身是对称的：必须恰好一方让步
aliceYields := aliceMgr.losesGlareTieBreak(bob, bobFP)
bobYields   := bobMgr.losesGlareTieBreak(alice, aliceFP)
if aliceYields == bobYields { t.Fatal("死局：双方都退或都不退") }
```

## 6. 并发模型

| 组件 | 并发方式 |
|---|---|
| `Transport` | 每连接 1 读 + 1 写 goroutine；事件经带缓冲 channel 上报 |
| `session.Manager` | 单事件循环（channel 收命令），状态无锁 |
| `crypto.Session` | `Seal` 仅写侧、`Open` 仅读侧调用，天然串行 |

`session.Manager` 用**单事件循环**而非互斥锁：状态转移集中在
`handleFrame` 一处，避免了锁顺序问题，也让"谁在什么时候改了状态"可追踪。

**注意**：`Manager` 会**独占消费** `transport.Events()` 通道。
外部代码（包括测试）不能再去读同一个通道——两者会竞争，谁拿到事件是随机的。
测试需要观察传输层事件时，必须另起一个独立传输层。
