# 公网穿透与中继设计

> 本文回答："两台设备隔着 NAT，怎么把数据送过去？"
> 首期（局域网）不实现本文内容，但 [transport-lan.md](transport-lan.md) §8 的接口已为其预留。

---

## 1. 一句话结论

**纯 P2P 在公网上不成立。** 必须有一台（或多台）**公网可达节点**承担：会合（交换地址）、STUN（地址反射）、中继（兜底转发）。

原因：**对称 NAT 与 CGNAT 下，打洞在原理上就无法成功**（见 §2.3）。任何声称"100% 纯 P2P、零服务器"的方案，在这个网络条件下都是在静默失败或已被降级为中继。

本文的设计目标是：**让绝大多数连接走直连（零服务器带宽成本），只为少数失败情况付中继成本**，并把这份成本控制住。

## 2. NAT 行为分类（决定了能不能打洞）

### 2.1 两个独立维度

NAT 行为由两个**互相独立**的维度决定（RFC 4787 定义了 UDP 的要求框架）：

**A. 映射行为**（内部地址如何映射到外部端口）

| 类型 | 行为 |
|---|---|
| Endpoint-Independent Mapping | 无论发给谁，同一内部端口映射到**同一外部端口** |
| Address-Dependent Mapping | 按目标 IP 分配端口 |
| **Address and Port-Dependent Mapping** | 按目标 IP:port 分配端口（**即对称 NAT**） |

**B. 过滤行为**（谁能从外部发进来）

| 类型 | 行为 |
|---|---|
| Endpoint-Independent Filtering | 任何外部主机都能发进来 |
| Address-Dependent Filtering | 只有内部先发过包的 IP 能发进来 |
| Address and Port-Dependent Filtering | 只有内部先发过包的 IP:port 能发进来 |

### 2.2 经典四分类

| 类型 | 映射 | 过滤 | 打洞难度 |
|---|---|---|---|
| Full Cone（NAT1） | Endpoint-Independent | Endpoint-Independent | 容易 |
| Restricted Cone（NAT2） | Endpoint-Independent | Address-Dependent | 容易 |
| Port Restricted Cone（NAT3） | Endpoint-Independent | Address and Port-Dependent | 中等 |
| **Symmetric（NAT4）** | **Address and Port-Dependent** | 任意 | **原理上不可打洞** |

**关键结论**：能否打洞取决于**映射行为**，不是过滤行为。过滤行为只影响"要不要先握手"。

> 注：上面这套四分类来自早期的 NAT 分类实践（RFC 3489 时代），RFC 5389/8489 已不再推荐用"分类"来描述 NAT，而是直接描述两种行为。工程上四分类仍是有效的沟通语言，但实现时应**直接按两个维度判断行为**，而不是套用旧的枚举。

### 2.3 为什么对称 NAT 打不通

```
A 的 NAT 是对称的：
  A → STUN服务器S1  : NAT 分配外部端口 30001
  A → 对端B的公网地址: NAT 分配外部端口 30002   ← 不同的端口！

A 通过信令告诉 B："我的地址是 <公网IP>:30001"
B 向 <公网IP>:30001 发包 → 但 A→B 方向的映射其实是 30002
                              → 包被丢弃
```

同时向对方公网地址发包的"打洞"技巧，**在对称 NAT 下失败**，因为 A 发往 B 时用的端口与 A 告诉 B 的端口不是同一个。

### 2.4 CGNAT（运营商级 NAT）

- 地址段 `100.64.0.0/10`（RFC 6598）
- 移动网络、部分宽带大量使用
- 通常叠加在**运营商自己的 NAT** 之上，形成**多层 NAT**
- 行为常为对称或受限，且**用户无法在运营商设备上配置端口转发**
- 这是打洞失败率最高的场景，也是"必须有中继"的根本原因

### 2.5 如何检测自己的 NAT 行为

用多个 STUN 服务器：

```
向 S1 请求 → 映射地址 M1
向 S2 请求 → 映射地址 M2
M1 == M2  ⟹ Endpoint-Independent Mapping（可打洞）
M1 != M2  ⟹ Address/(Port)-Dependent Mapping（对称，打洞无望）
```

- libp2p 的 **AutoNAT** 就是这个思路：它会主动探测自己是否可被外部直连，并在不可达时保留中继地址。
- 实现建议：把探测结果缓存在本地，**网络变化（换 WiFi/切蜂窝）时失效重测**。

## 3. 穿透技术矩阵

| 技术 | 成功率（经验值） | 服务器成本 | 依赖 | 稳定性 |
|---|---|---|---|---|
| **IPv6 直连** | 高（若双方均有公网 v6） | 零 | ISP 支持、防火墙允许 | 高 |
| **UPnP / NAT-PMP / PCP** | 家用路由约 50–70% | 零 | 路由器开启该功能 | **高**（真端口映射） |
| **STUN + UDP 打洞** | 见下 | 极低（KB 级） | STUN 服务器 | 中（依赖映射保活） |
| **TCP 打洞** | 明显低于 UDP | 低 | 需 OS 支持同时打开 | 中 |
| **端口预测 / Birthday Paradox** | 中（仅对顺序分配端口的 NAT） | 高（上千包） | — | 低 |
| **TURN / Relay 中继** | **100%** | **高（双向带宽）** | 中继服务器 | 高 |

**关于成功率**：常被引用的一组 WebRTC 社区经验值是"约 80% 的连接可通过打洞建立，其余约 20% 需 TURN"。这个比例**高度依赖用户网络构成**（移动网络、CGNAT 占比越高越差），且我无法在离线环境核实具体数字。**请视为量级参考，并自行在同网环境中实测**。

### 3.1 为什么优先 UDP 而不是 TCP 打洞

- TCP 的 `SYN` 重传窗口给了极窄的时间窗，错过即失败；
- 各 NAT 对 TCP 的处理差异远大于 UDP；
- 需要操作系统支持 TCP simultaneous open（部分平台默认关闭）；
- 结论：**用 UDP 打洞**（QUIC 或 ICE over UDP），在 UDP 之上再实现可靠性。

### 3.2 为什么 UPnP 值得单独实现

UPnP/NAT-PMP/PCP 得到的不是"打洞"而是**真实的端口映射**：

- 映射一旦建立就是**稳定**的，不像打洞依赖 NAT 映射保活；
- 无需 STUN，无需信令协调时机；
- 家庭宽带场景成功率高。

代价：企业网络基本不可用；UPnP 长期被批评为不安全（任何本机程序都能开端口），因此应作为**可选功能**，并在首次使用时向用户说明。

## 4. 必选基础设施：至少一个公网节点

无论选哪种穿透技术，都必须有公网可达节点提供以下能力：

| 能力 | 作用 | 流量量级 |
|---|---|---|
| **会合 / 信令（Rendezvous）** | 交换候选地址、协调打洞时机、通知 ICE restart | 极小（KB 级） |
| **STUN** | 反射地址发现（"我的公网地址是什么"） | 极小 |
| **TURN / Relay** | 打洞失败时的兜底转发 | **大（双向）** |

### 4.1 关键认识：前两者几乎免费，第三者才是成本

- STUN 与信令只传几百字节的控制信息，一台最便宜的 VPS 就能服务大量用户；
- **中继转发是带宽成本**：中继一份数据，服务器要**收一份 + 发一份**，即流量翻倍计费。

因此整个设计的成本优化目标非常明确：**最大化直连比例，最小化中继使用**。

### 4.2 能否使用公共 STUN 服务

**可以，而且推荐用。** 但必须清楚公共 STUN 能替代什么、不能替代什么。

#### STUN 是唯一"免费可持续"的组件

原因在于它的流量特征与 TURN 有本质区别：

| 特征 | STUN | TURN |
|---|---|---|
| 单次请求/响应 | 几十~上百字节 | — |
| 一次性用量 | 每端几个包（Binding Request/Response） | 分配请求 |
| 长期保活 | 每 15~30s 一个包 | 每几秒一个包 |
| **是否承载媒体流量** | **否**——反射完地址即退场 | **是**——转发全部数据，**双向计费** |

**STUN 只回一句话就退场，之后双方直接通信**。这是它能被免费提供、而 TURN 从来没人免费提供的根本原因。

因此实践中普遍使用公共 STUN（`stun.l.google.com:19302` 是最常被引用的）。

> **待验证**：我无法在离线环境核实各公共 STUN 服务商的官方使用条款与限速策略。上线前请自行查证。

#### 公共 STUN 不能替代的两件事

| 环节 | 谁负责 | 公共 STUN |
|---|---|---|
| 发现自己的公网映射（srflx 候选） | STUN | ✅ |
| 探测 NAT 行为（对称与否，§2.5） | STUN（多服务器对比） | ✅ |
| **交换候选地址给对端** | **会合/信令服务器** | ❌ **完全不能** |
| 打洞时机协调 | ICE 内部 / DCUtR | ❌ |
| 打洞失败时转发数据 | **TURN** | ❌ |

**关键**：公共 STUN 服务器不会告诉对端你在哪，也无法让两个客户端互相知道对方存在。**必须自己部署会合/信令服务器**。

所以问题不是"用公共 STUN 能否省掉服务器"，而是"能否省掉**自己那台 STUN**"。答案是：能，但建议仍然自建一台（见下）。

#### 公共 STUN 的三个真实约束

**1. 无 SLA，可能随时失效**

- 说停就停、说限速就限速；
- **部分网络会屏蔽或干扰公共 STUN**，尤其是：
  - 对国外服务可达性受限的网络（如中国大陆对 Google 服务）；
  - 企业/校园网络对未知 UDP 出站的限制；
  - 某些 ISP 对所有非 443 端口 UDP 的粗暴处理。

**后果**：srflx 候选收集失败时，用户会**静默退化为"只能同局域网"**，日志里只有一个 timeout——**极难排查**。这要求在 UI 与日志中显式暴露该失败（见 §13.2）。

**2. 多服务器是必须的，不是优化**

单个 STUN 无法探测 NAT 行为。§2.5 的判定要求对比**两个不同地址的服务器**：

```
向 S1 请求 → 映射端口 P1
向 S2 请求 → 映射端口 P2
P1 == P2  ⟹ Endpoint-Independent Mapping，可打洞
P1 != P2  ⟹ 对称 NAT，打洞无望
```

**实际的坑**：若 S1 与 S2 位于同一数据中心、同一出口 IP 段，某些 NAT 产生的映射可能恰好相同，导致把**对称 NAT 误判为可打洞**。因此：

- 服务器应**分布在不同网络位置**；
- 判定应基于**多数投票**而非单次对比（至少 3 个服务器）。

**3. 不要把公共 STUN 当作保活工具**

NAT 映射会在空闲后被回收（常见 30s~5min）。用 STUN 周期性发包维持映射是**误用**：

- 对公共服务器是滥用（占用其请求配额）；
- 正确做法是用**已有连接上的应用层心跳**（[transport-lan.md](transport-lan.md) §5.1 的 30s `PING`）维持映射；
- ICE 有自己的 consent freshness 机制处理其链路，让它正常工作即可，**不要另起 STUN 流量去干扰**。

#### 建议：公共 + 自建混合

```
配置为有序列表，按优先级尝试：

1. 自建 STUN（同一台 VPS）          ← 首选
2. 自建 STUN 的备用地址/端口
3. 公共 STUN 列表                    ← 兜底
   - stun.l.google.com:19302
   - 其他公共节点（需自行验证可达性与条款）
```

**为什么仍要自建**：

- **成本几乎为零**：你为信令已经租了 VPS，STUN 只是同一个进程多监听的几个包；
- **日志可控**：不把用户 IP 暴露给第三方；
- **可达性可控**：在公共 STUN 被屏蔽的网络里，自建的那台能顶上；
- 反向也成立：自建 VPS 挂掉时，公共 STUN 作为冗余。

**成本测算**：1 万用户每 20 秒发一个 100 字节的保活包 ≈ `10000 × 100 B / 20 s = 50 KB/s`——对任何 VPS 都是噪声级别。

#### 一个行不通的替代思路

有人尝试用**信令服务器**充当反射点（信令走 WebSocket，服务器天然能看到公网 IP:port），以省掉 STUN。**对 UDP 打洞行不通**：

- TCP/WebSocket 连接的源端口与你将要用于 UDP 打洞的端口**必然不同**；
- NAT 会为不同协议/端口分配不同映射，因此信令观察到的是 **TCP 映射**，**不能用作 UDP 候选**。

例外：**TCP 打洞**场景下该信息可用，但 TCP 打洞成功率明显低于 UDP（§3.1）。

**结论：UDP 打洞离不开 STUN。**

## 5. 方案选型

### 5.1 三个候选

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. pion/webrtc**（DataChannel） | 用 WebRTC 的 ICE + DTLS + SCTP | ICE 是解决此问题的**标准协议**（RFC 8445），成熟；纯 Go；提供可靠有序传输；TURN 客户端与服务器（pion/turn）都有 | 引入 DTLS/SCTP 栈（与我们应用层 E2EE 有部分功能重叠）；依赖不小 |
| **B. go-libp2p** | DCUtR 打洞 + Circuit Relay v2 + AutoNAT + QUIC | 一站式；DCUtR 设计现代；Circuit Relay v2 自带资源限制 | 依赖很重；API 复杂；需自建 bootstrap/relay |
| **C. 自建 UDP 打洞 + 自建 relay** | 自己实现 STUN 客户端、打洞协调、中继 | 最轻、最可控 | **工作量大且易错**：NAT 行为差异、时机协调、保活、重试都要自己处理 |

### 5.2 推荐：方案 A（pion）

**理由**：

1. **ICE 就是为这个问题设计的标准**。它已经解决了候选收集、配对、连通性检查、优先级、ICE restart——自己重造这些是负收益。
2. **纯 Go，与 Gio 集成自然**，交叉编译到桌面/移动无额外工具链。
3. **pion/turn 可直接自建 TURN 服务器**，不必依赖第三方服务。
4. **DataChannel 提供可靠有序传输**，省去在 UDP 上自己实现可靠传输（那是重造 SCTP）。
5. **ICE 天然支持"打洞失败自动降级 TURN"**，正好对应我们"最大化直连、兜底中继"的目标。

**关于 DTLS 冗余的解释**：WebRTC 自带 DTLS 加密，而我们有应用层 E2EE，看似重复。但这**不是浪费**：

- DTLS 保护"传输跳"（对 TURN 隐藏内容之外的信息）；
- 应用层 E2EE 保护"端到端"（不依赖传输层实现）；
- 两者独立，任何一层被攻破另一层仍有效；
- 更重要的是：**若未来改用 Circuit Relay v2 或自定义 relay，可能没有 DTLS 保护，应用层 E2EE 是唯一保障**。

**注意**：pion 的模块路径、API 与版本演进较快，实现前需核对当前版本（`pion/webrtc`、`pion/ice`、`pion/stun`、`pion/turn`、`pion/dtls`、`pion/sctp`）。我无法离线确认各模块最新版本与 API。

### 5.3 不选 libp2p 的取舍

libp2p 并不差，若未来需要 DHT、多协议互通、更丰富的中继资源控制，它是更完整的选择。当前不选是因为**依赖重量与复杂度**对一个聊天应用过重（二进制显著增大、构建变慢、API 学习成本高）。这是一个可逆的决策——`transport.Transport` 接口抽象保证了两者可以互换。

## 6. ICE 工作流程

```
① 候选收集（Gathering）
   双方各自收集候选地址：
   ├─ host    : 本机接口地址（局域网/公网）
   ├─ srflx   : 经 STUN 得到的公网映射（Server Reflexive）
   └─ relay   : 经 TURN 分配的中继地址
       ↑ ICETransportPolicy 可控制是否收集 relay 候选
         （先只收集 host+srflx 尝试直连，失败再收集 relay，可显著降本）

② 信令交换（Signaling）
   通过会合服务器交换候选列表
   ↑ 必须认证（见 §8）

③ 连通性检查（Connectivity Checks）
   按优先级配对候选，互发 STUN Binding Request
   成功的配对中选出优先级最高的（host > srflx > relay）

④ 建立传输
   ICE 通路 → DTLS 握手 → SCTP 关联 → DataChannel 打开

⑤ 完成
   之后 DTLS 记录的载荷即我们的帧
```

### 6.1 关键优化：延迟收集 relay 候选

`relay` 候选的收集会在 TURN 服务器上分配资源并开始产生开销。若在收集阶段就把 relay 候选一起发出，即使最终直连成功，也浪费了 TURN 分配。

**建议**：先只收集 `host` + `srflx`，等待直连尝试结果；**仅在打洞失败后**再触发 relay 候选收集。pion 支持通过 `ICETransportPolicy` 与自定义候选策略影响该行为（具体 API 需核对版本文档）。

## 7. 分层连接策略

综合所有技术，形成完整的降级链：

```
L0  IPv6 直连          — 若双方都有公网 IPv6 且防火墙允许，直接连
L1  局域网（已实现）    — mDNS + TCP，同网段
L2  UPnP / NAT-PMP     — 请求路由器开端口映射，得到稳定直连
L3  ICE 打洞           — STUN 得到 srflx 候选，配对打洞（覆盖 Cone NAT）
L4  TURN 中继          — 兜底，100% 可用，但有带宽成本
```

**实现要点**：

- **L0/L1 应优先尝试**：它们零成本且最稳定。局域网发现已在首期实现，公网阶段不应被新通道取代。
- **L2 可选**：作为独立开关，用户可选择是否允许使用 UPnP。
- **L3→L4 的降级要有时限**：不要让用户无限等待打洞。建议打洞超时（如 5–10s）后立即启用中继。
- **中继→直连的"升级"**：若当前走中继，但 ICE 发现直连变得可行（例如 NAT 映射变化后），应**主动切换回直连**以省成本。ICE 本身支持候选切换，但需要信令通道配合。

## 8. 信令与安全

### 8.1 信令通道做什么

| 消息 | 内容 |
|---|---|
| `REGISTER` | 用身份公钥证明在线，注册可达方式 |
| `LOOKUP` | 查询对端是否在线 |
| `CANDIDATES` | 交换 ICE 候选列表 |
| `RESTART` | 通知 ICE restart |
| `HANGUP` | 结束会话 |

### 8.2 【关键】信令消息必须签名

信令服务器是**不可信**的（我们自己部署也不该无条件信任）：

- 若攻击者能注入伪造的候选地址，可把连接引导到自己的机器 → 应用层指纹验证会**最终**发现（[crypto-protocol.md](crypto-protocol.md) §6.4），但那是"事后发现"，期间可能已造成可观测的连接行为泄露；
- 因此信令消息应使用**身份密钥签名**，接收方验证签名后才采信候选地址。

**这意味着**：信令服务器即使被完全控制，也**无法实施 MITM**（它没有私钥），最坏能做的是**拒绝服务**（丢弃/篡改消息导致连接失败）和**元数据观察**。

### 8.3 信令服务器能看到什么

- 谁在找谁（社交图！）
- 在线状态与时间
- 候选地址（IP 地址）

这是**明确的元数据泄露**，与 [threat-model.md](threat-model.md) 的声明一致。若需要隐藏社交图，需要更复杂的方案（匿名会合、onion 路由），**超出范围**。

### 8.4 第②步的时机协调

UDP 打洞要求双方**几乎同时**发包。协调查方法：

- 双方各自通过信令告知"我准备好了"，收到对端"准备好"后立即开始发送；
- 或由信令服务器指定一个统一启动时间（需考虑时钟偏差）；
- DCUtR 用 `Connect` + `Sync` 两次往返来同步。

ICE 内部已处理连通性检查的时机，因此**用 ICE 时不需要自己协调**——这是选 pion 的又一个理由。

## 9. 中继成本控制

中继是唯一会随用户规模线性增长的成本项。控制手段：

| 手段 | 效果 |
|---|---|
| **优先直连**（§7） | 从源头减少中继使用 |
| **延迟收集 relay 候选**（§6.1） | 避免"直连成功后仍占用 TURN 分配" |
| **中继→直连主动升级** | 缩短中继使用时长 |
| **只在打洞失败后启用** | 避免无谓中继 |
| **限制每用户带宽**（如 256 KB/s） | 防止单用户占满 |
| **限制并发中继会话数** | 防止资源耗尽 |
| **限制单会话时长**（如 30 分钟，之后强制重试直连） | 防止长期占用 |
| **认证**：只有注册用户可用中继 | 防止被当作免费代理/开放中继滥用 |
| **流量配额** | 防止滥用 |

### 9.1 成本估算（帮助做容量决策）

假设：100 个活跃用户，其中 20% 走中继，每用户平均速率 10 KB/s。

```
中继流量 = 100 × 0.20 × 10 KB/s × 2（双向）
         = 400 KB/s ≈ 3.4 Mbps 持续
         ≈ 400 KB/s × 86400 s/天 × 30 天 ≈ 1.04 TB/月
```

> 以上为**示例推算**，实际取决于用户行为（是否频繁传附件会显著抬高）。附件传输是中继成本的主要放大器——见 §10.2。

**建议**：中继服务优先选择**按流量计费**而非按带宽计费的方案，避免为峰值预留付费。

### 9.2 是否允许中继传附件

一个务实的问题。若允许，一个用户传 1 GB 附件就会产生 2 GB 中继流量。

建议策略：

- 小文件（如 < 1 MB）允许走中继；
- 大文件在仅中继可达时**拒绝**，并提示"需要直连才能传输大文件"；
- 或对大文件设**每日中继配额**。

这是一条**产品取舍**，需与用户确认（见 §14）。

## 10. 与现有设计的关系

### 10.1 应用层 E2EE 不受影响（这是关键优势）

我们的 E2EE 在应用层，与传输层解耦：

```
[应用层]  我们的 AEAD（端到端，中继无法解密）
   ↑
[传输层]  DTLS（端到端，TURN 中继无法解密，因为它只转发 UDP 包）
   ↑
[TURN]    只看到密文 UDP 包 + 元数据（IP、端口、大小、时间、时长）
```

**中继无法读取消息内容**，只能做流量分析。

### 10.2 附件走中继的成本敏感性

附件（见 [attachments.md](attachments.md)）会大幅抬高中继流量。设计附件时需配合：

- 附件块**不应**比聊天消息有更高优先级（见 [attachments.md](attachments.md) §6）；
- 大附件在仅中继可达时应提示用户成本/被拒绝（§9.2）。

### 10.3 接口扩展需求

现有的 `transport.Transport`（[architecture.md](architecture.md) §3.3）需要为公网扩展：

| 需求 | 现状 | 说明 |
|---|---|---|
| 多候选地址 | `PeerInfo.Addrs []net.Addr` ✅ | 已支持，正好对应 ICE 候选 |
| 地址更新事件 | ❌ | 打洞成功后地址变化，需要新事件类型 |
| 连接类型上报 | ❌ | UI/成本控制需知道"当前是直连还是中继" |
| 可重试性区分 | ⚠️ | `Send` 错误需区分"暂时不可达"与"永久失败" |
| ICE restart | ❌ | 网络切换后需要重新协商 |

**建议新增事件**：

```go
type ConnUpgraded struct { ID PeerID; Path ConnPath }  // 中继→直连
type ConnPathInfo struct {                             // UI 可展示
    Kind  string   // "direct" | "relay"
    Addrs []string
}
```

**UI 应展示当前是直连还是中继**——这既是透明度要求，也让用户理解为何有时延迟高。

## 11. 保活与网络变化

### 11.1 NAT 映射保活

- UDP 映射若无流量会被 NAT 回收，RFC 4787 建议至少 2 分钟，实际常见 30s–5min；
- 现有心跳为 30s（[transport-lan.md](transport-lan.md) §5.1），**足以维持映射**；
- 但 ICE 有自己的 consent freshness 机制（STUN binding 往返），应让其正常工作，不要用自己的心跳去干扰。

### 11.2 网络切换

这是移动端的高频场景（WiFi ↔ 蜂窝）：

- 所有已有 NAT 映射**立即失效**；
- 所有候选地址失效（本地 IP 也变了）；
- 需要 **ICE restart**：重新收集候选、经信令交换、重新连通性检查；
- **信令通道必须能在网络切换后重连**。

**设计要点**：不要把"连接"当作长期稳定的东西。UI 应能优雅展示"正在重新连接"，而不是报错。

## 12. 部署清单

最小可行基础设施：

| 组件 | 选型 | 说明 |
|---|---|---|
| VPS | 任意云，1–2 核 / 1–2 GB / 公网 IPv4（**强烈建议同时有 IPv6**） | 按流量计费 |
| STUN | **自建为主 + 公共为备**（见 §4.2）；`pion/turn` 自带 STUN 能力，或 coturn | 可与应用共进程，成本可忽略 |
| TURN | `pion/turn`（Go，可与应用同进程）或 coturn（C，更成熟） | 需配置长期凭据认证 |
| 会合/信令 | 自写（WebSocket + 签名验证） | 是本项目需要自己实现的部分 |
| TLS 证书 | Let's Encrypt | 信令走 WSS |

**STUN 部署建议（见 §4.2）**：

- 自建 STUN 与信令共用同一台 VPS（成本增加可忽略）；
- 客户端配置为**有序列表**：自建优先，公共 STUN 兜底；
- 用于 NAT 行为判定的服务器**必须分布在不同网络位置**，且用**至少 3 个**做多数投票，否则会把对称 NAT 误判为可打洞；
- 若面向中国大陆用户，**必须有自建 STUN**——公共 STUN 可达性不具备保障。

**选 coturn vs pion/turn**：

- coturn：成熟、功能全、运维资料多；但需单独部署与配置；
- pion/turn：Go 库，可与应用同进程，便于统一运维；成熟度低于 coturn。

> 我无法离线确认两者当前的最新版本与功能对等程度，实现前需评估。

## 13. 测试要点

### 13.1 需要覆盖的 NAT 组合

在实验室环境中用 iptables/nftables 模拟不同 NAT 行为，构造组合矩阵：

| 本端 | 对端 | 期望 |
|---|---|---|
| Full Cone | Full Cone | 打洞成功，直连 |
| Port Restricted | Port Restricted | 打洞成功，直连 |
| **Symmetric** | Full Cone | **打洞失败 → 中继** |
| **Symmetric** | **Symmetric** | **打洞失败 → 中继** |
| 双层 NAT（家路由 + 模拟 CGNAT） | 任意 | 依行为判定 |
| IPv6 双方可用 | — | 直连，不走中继 |
| 一方 IPv4-only | 一方双栈 | 回退 IPv4 |

### 13.2 其他用例

| 场景 | 期望 |
|---|---|
| TURN 服务器不可达 | 明确报错，不静默失败 |
| **所有 STUN 都不可达** | **UI 显式提示"无法建立公网直连"**，不是静默退化 |
| **自建 STUN 不可达，公共 STUN 可用** | 自动切到公共 STUN，连接仍能建立 |
| **公共 STUN 不可达，自建可用** | 自动切到自建 STUN |
| **两个 STUN 返回相同映射**（NAT 行为判定） | 判为可打洞，尝试直连 |
| **两个 STUN 返回不同映射**（对称 NAT） | 判为对称，直接走中继，不做无谓打洞 |
| **≥3 个 STUN 投票** | 单台异常不影响判定结果 |
| 中继传输中直连变得可用 | 升级为直连（若实现该功能） |
| 网络切换（WiFi→蜂窝） | ICE restart 成功，会话不中断（或明确提示） |
| UPnP 请求被路由器拒绝 | 静默回退到 L3，不报错 |
| 信令消息被篡改 | 签名验证失败，拒绝该候选 |
| 伪造候选地址注入 | 验证失败；即使通过，应用层指纹校验兜底 |
| 长期中继会话 | 触发时长限制并重试直连 |
| 中继带宽超限 | 限速生效，不拖垮服务器 |

## 14. 待定问题（需要产品决策）

| 问题 | 影响 | 建议 |
|---|---|---|
| 是否自建 TURN 还是用第三方 | 成本、隐私、运维 | 自建优先（元数据不外泄给第三方） |
| **STUN 用公共还是自建** | 可达性、隐私、可排查性 | **自建为主 + 公共为备**，见 §4.2 |
| **选用哪些公共 STUN 及其条款** | 合规与稳定性 | **需自行查证**（本设计未验证） |
| 中继是否允许传大附件 | 成本 vs 可用性 | **需明确决策**，见 §9.2 |
| 是否实现 UPnP | 稳定性 vs 安全争议 | 做成可选开关 |
| 中继→直连升级是否首期实现 | 成本优化 vs 复杂度 | 建议实现（收益明确） |
| 是否支持 IPv6-only 网络 | 覆盖面 | 建议支持，监听双栈 |
| 信令服务器是否兼做离线消息 | 架构范围 | **不建议**，会显著改变隐私模型 |

## 15. 一句话总结

> 用 **ICE（pion）** 解决打洞，**STUN 自建为主、公共兜底**，用**自建 TURN** 兜底转发，用**身份密钥签名**保护信令，用**延迟收集 relay 候选 + 中继→直连升级 + 大附件拒绝**控制成本。
> 接受"必须有公网节点"这一事实，把优化目标定在**最大化直连比例**，而不是追求不存在的"纯 P2P"。
>
> **公共 STUN 可以省掉一台 STUN 服务器，但省不掉会合服务器，也省不掉 TURN。**
