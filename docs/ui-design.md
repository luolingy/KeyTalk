# 界面设计系统（方案 C：安全优先）

> 本文档记录 `internal/ui` 的视觉与交互决策。
> 改界面前请先读这一页——里面的规则多数不是审美偏好，而是安全要求。

## 1. 为什么"好看"不是第一目标

本项目已经出现过三个真实缺陷，性质完全相同：

| 缺陷 | 界面当时显示的内容 | 实际状态 |
|---|---|---|
| 联系人行点不动 | "请选择联系人" | 用户点了，代码没收到 |
| `StateChanged` 全映射为 secure | "已加密" | 一方还在握手 |
| `PeerLost` 从未发出 | "已连接" | 对端早已退出 |

**三个都是"界面显示了不真实的状态"。** 因此本界面的第一目标是
**让用户看到真相**，其次才是美观。

由此产生三条硬规则，改动界面时不得违反：

### 规则 1：信任状态常驻，不可折叠

顶部信任条占用 44dp 永久空间，没有关闭按钮。

理由：本工具的信任是"默认不安全、需要用户主动动作才能变好"。
可关闭的横幅会被用户在第一次就关掉，此后永远看不到——
而那正是提示最需要出现的时候。

### 规则 2：未核实时，每条消息都带标记

未核实身份的会话，其每条消息左侧有一条琥珀色竖带，
气泡内还有一行"未核实身份"。

理由：把信任状态只放在顶部会被忽略——用户读消息时不看顶部。
标记贴在消息本身上，用户在阅读内容时无法避开，
且不打断操作，因此不会被关掉。

### 规则 3：指纹与 emoji 常驻可见

本机指纹在信任条右侧；对端指纹在会话标题下；
emoji 在会话上方。
全部不藏进设置页。

理由：带外核对是防中间人的**唯一**手段。
每多一次点击，被跳过的概率就显著上升。

## 2. 四档信任等级

`TrustLevel`（见 `trust.go`）是**唯一**的信任推导入口。
顶部信任条、联系人圆点、消息色带全部调用 `trustOf()`。
任何一处自行判断都会产生不一致——而"界面各处对信任的表述不一致"
本身就是安全缺陷：用户会相信最乐观的那一处。

| 等级 | 颜色 | 含义 | 触发条件 |
|---|---|---|---|
| `TrustUnknown` | 灰 | 未连接 | 无会话 / 离线 / 握手中 |
| `TrustUnverified` | **琥珀** | 已加密，但未核实身份 | 握手完成，用户未确认 |
| `TrustVerified` | 绿 | 已核实身份 | 用户比对过 emoji |
| `TrustFailed` | 红 | 失败 | 握手失败 |

### 2.1 为什么必须分四档而不是两档

这是本设计**最重要**的一条。

把"已加密但没核实"与"已核实身份"合并成"安全"，
是这类工具最常见也最有害的偷懒：用户会把
**"内容没有被窃听"** 读成 **"我知道对面是谁"**。

这是两件完全不同的事：

- **加密**解决"有没有人在听"——握手自动达成；
- **emoji 核对**解决"对面是不是那个人"——**只有人能保证**。

因此 `trustPhrase()` 在未核实状态下必须同时出现
"已加密"与"未核实身份"两个信息（有单测断言，
见 `TestTrustPhraseDistinguishesEncryptionFromIdentity`）。

### 2.2 为什么用琥珀而不是红色

`TrustUnverified` 是**初始状态**，不是错误。
用红色会让每一个新会话看起来都像被攻击了，
用户会对告警脱敏——等真正的 `TrustFailed` 出现时就不再有分量。

### 2.3 实心/空心的区分

`trustDot()` 里已核实用实心，其余用空心环。
这样在**没有颜色**的情况下也能分辨，对色觉障碍用户同样是可用的。

## 3. 配色

| 用途 | 值 | 说明 |
|---|---|---|
| 背景 | `#0A0A0B` | 近黑而非纯黑：纯黑配纯白在多数 LCD 上发糊 |
| 表面 | `#131416` | 侧栏、信任条、状态栏 |
| 抬起 | `#1C1E21` | 气泡、输入框、悬停 |
| 分隔线 | `#25282C` | 仅用于必要处，层级主要靠明度差 |
| 强调 | `#2DD4BF`（青） | **只此一种** |

强调色刻意只用一个：颜色在本界面里是要**承担语义**的资源
（灰/琥珀/绿/红四档信任）。五颜六色的强调色会稀释掉
这三个状态的分量。

选青色而非蓝色：与常见聊天软件的蓝区分开，
避免用户把本工具误认成普通即时通讯产品。

## 4. 布局

```
┌──────────────────────────────────────────┐
│ 常驻信任条（色带 + 状态 + 本机指纹）        │ ← 44dp，不可折叠
├────────────┬─────────────────────────────┤
│ 联系人列表  │ 会话标题（名称 + 指纹 + 药丸）│
│  280dp     ├─────────────────────────────┤
│            │ emoji 核对面板（会话建立后）  │
│  圆点=信任  ├─────────────────────────────┤
│            │ 消息流（气泡 + 信任色带）     │
│            ├─────────────────────────────┤
│            │ 输入框（圆角）+ 发送按钮      │
├────────────┴─────────────────────────────┤
│ 状态栏（字体状态 / 最近错误 / 提醒）        │
└──────────────────────────────────────────┘
```

没有任何联系人时，右侧整块显示**引导页**而不是
"请选择联系人"——后者在列表为空时是一句无意义的话，
用户根本无从选择，需要的是"怎么才能有联系人"。

## 5. 首次引导页

`onboarding.go`。三部分：

1. **"没有服务器，也没有账号"** —— 解释这是设计选择而非功能缺失。
   不解释，用户会一直找注册入口。
2. **三步操作指引** —— 给出具体命令。
3. **"为什么需要核对 emoji？"**（重点）

第 3 段是整个界面上最重要的文字。用户会问
"别的软件扫个码就行了，为什么你要我念 emoji"。
不回答，用户就会把核对当成可跳过的仪式，
于是安全属性名存实亡。

## 6. Gio 实现要点

| 事项 | 做法 |
|---|---|
| 填充背景 | 无原语，用 `paint.FillShape` + `clip.Rect`；**用 Max 不用 Min**（Flexed 布局里 Min 可能是 0） |
| 圆角 | `clip.RRect` |
| 背景包内容 | `layout.Background{}.Layout(gtx, bg, content)` 两个 widget |
| 尺寸依赖内容的底色 | `op.Record` / `op.Defer` 先量再画 |
| 圆点 | `clip.Ellipse{Min, Max}` |

### 6.1 必须持久化的状态

`widget.Clickable` **必须**跨帧持久保存：

```go
btn := new(widget.Clickable)   // ❌ 永远收不到点击
```

这个缺陷在本项目中**出现过两次**：一次在发送按钮（当时发现了），
一次在联系人行（当时没发现，导致"点联系人打不开聊天界面"）。

现行做法：
- `sendBtn`、`emojiAck` —— 单个字段
- `rowClicks []widget.Clickable` —— 按行索引的切片，
  数量变化时同步扩容/截断（见 `contactRows`）

**新增任何可点元素时，先确认它的 Clickable 存在哪里。**
